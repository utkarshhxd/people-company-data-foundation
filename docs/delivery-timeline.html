04 Critical path

Four phases determine the completion date. Everything else has slack.

P1 → P5 → P9, with P8 joining before sign-off. The chain is real, not administrative: scale results can force schema or batching changes, and P5 touches resolution and the golden record — the two stages most affected by those changes. Doing P5 first would mean doing it twice. P9 cannot begin until security review closes, because acceptance on a system that is about to change its auth model proves nothing.

Genuinely parallel: P2 (CI), P3 (API auth), P4 (alerting) and P7 (Excel) share no code with the critical path and depend on nothing in it. A second engineer taking that track compresses delivery to roughly 5–6 weeks, because the critical path alone is 13–20 engineer-days. Note that P3 must still precede P8, so the parallel track has its own internal order.

The single highest-leverage decision is confirming real production file sizes before week 1. If files are tens of thousands of rows rather than millions, P1 shrinks from 6–9 days to 2–3 and the whole plan pulls in by a week.

06 Risks

Drawn from what is actually observable in the codebase today, not generic project risk.

R1 The pipeline has never run at scale HighCritical path
Why
The largest file ever processed is 19 rows. resolution/pipeline.py:145 commits once per record and runs three queries per record, which at 500k records is 500k transactions and 1.5M queries. Correctness is well tested; throughput is entirely unmeasured.
Affects
P1, and therefore everything downstream of it
Impact
+5 to +10 days if batching needs restructuring rather than tuning
R2 Table growth is multiplicative, by design HighCritical path
Why
The lossless guarantee means attribute_observation holds one row per cell — 500k records × 30 columns is 15M rows. validation_result stores passes as well as failures and may grow larger still. Both were deliberate choices with documented reasoning, but the volume consequence is untested.
Affects
P1; may force partitioning work inside P5
Impact
+3 to +5 days for partitioning and retention policy
R3 Match precision has never been measured High
Why
Matching is verified by construction — hand-built fixtures where the right answer is known. There is no labelled evaluation set, so false-merge and false-split rates on real data are unknown. Blocking on a common company name could also produce very large candidate sets.
Affects
P1 (performance), P5 (thresholds), P9 (acceptance)
+5 days to build an evaluation set and tune, if precision proves poor
R4 No high availability, and the constraint that forbids it MediumScope decision
Why
Kafka runs as a single broker with replication factor 1 and Postgres as a single instance. That is correct for the local-first specification, which explicitly excluded Kubernetes. If production means "survives a node failure", the architecture constraint has to be revisited — that is a decision for you, not a defect.
Affects
Outside the current plan; would add a phase
+10 days or more if HA is in scope — needs a decision before week 7
R5 Mapping quality depends on vocabulary coverage MediumOngoing
Why
The canonical vocabulary is accumulated knowledge of what vendors call things. A new vendor with unfamiliar column names produces review items rather than bad data — the system fails safe — but someone has to work that queue or the values stay unattributed and unusable.
Affects
P9 acceptance, and operations indefinitely
Not a schedule risk; a standing staffing commitment
R6 Knowledge concentrated in one engineer Medium
Why
One person built all ten increments. The ten ADRs mitigate this well — every non-obvious decision has its reasoning recorded — but no one else has operated the system. The runbook drill in P6 is the concrete test of whether the documentation is sufficient.
Affects
P6, P9, and all post-launch operations
+3 to +5 days if the runbook drill exposes gaps
R7 Development environment friction Low
Why
Windows Application Control blocks native Python extensions outside Docker, so every test run is a container run. Docker Desktop also crashed twice during the build. Neither is a defect, but both cost iteration speed and will do so throughout.
Affects
Every phase
Roughly 10% overhead, already priced into the ranges

07 Assumptions

Marked explicitly rather than absorbed silently. Each one changes the plan if wrong.

Confirm these before committing to dates

  1. Production means a single-host Docker Compose deployment, consistent with the local-first specification and its exclusion of Kubernetes. High availability is not in scope. See R4.
  2. Real vendor files are 100k–1M rows. Inferred from the original exports, which carried thousands of trailing blank rows. Unconfirmed — the largest file actually processed is 19 rows. This single number drives P1 and therefore the whole schedule.
  3. One engineer, five-day weeks, ~6 productive hours per day. Matches the pace of the ten completed increments. A second engineer on the parallel track compresses delivery to 5–6 weeks.
  4. No external review cycles beyond the UAT in week 9. Security or architecture review boards would add calendar time that is not budgeted here.
  5. The canonical vocabulary is adequate for the vendors in scope. New vendors produce review queue items rather than delays, but a materially different data source could require vocabulary work not costed here.
