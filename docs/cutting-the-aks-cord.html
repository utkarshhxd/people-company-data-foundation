A conversation, start to finish

Cutting the AKS Cord

How the PCDF pipeline went from "running on Azure's managed Kubernetes" to "running on three — well, one — plain Linux VMs we manage ourselves," told as a conversation between two people, one of whom just wants it explained simply.

MAYA — new-ish to the infra side, asking the questions
DEV — was in the room for all of it, explaining
Chapter 1 — Where this even started
MAYA

Okay, so I heard we "moved off AKS." Before we get into that — what even is PCDF? What was running before any of this?

DEV

PCDF is a data pipeline. Vendors send us company and contact data — CSV exports, mostly — and the system ingests each file, figures out what its columns mean, cleans it up, checks it against rules, works out when two rows from different vendors are actually the same real company, and merges everything into one "golden record" per entity, keeping a trail of exactly which vendor said what.

It's a handful of small services doing that in sequence — ingestion, mapping, normalization, validation, resolution, golden — plus a database, a message queue between the stages, a watcher that notices new files, and a review console where a human looks at anything the system isn't sure about.

MAYA

And all of that was running on Azure, in AKS. What's AKS again, exactly?

DEV

Azure Kubernetes Service. Kubernetes is the thing that actually runs all those little services — it decides which machine each one lands on, restarts anything that crashes, that sort of housekeeping. AKS is Microsoft's version of "we'll run Kubernetes for you" — you don't manage the control plane, you just describe what you want running and Azure keeps a Kubernetes cluster alive underneath it.

Alongside it we had ACR — Azure Container Registry — which is just where our built application images lived, so the cluster had somewhere to pull them from.

MAYA

Sounds convenient. So why touch it at all?

DEV

Two separate things happened, more or less at once. First, Elad wanted the cluster provisioned properly — through Terraform, not someone typing az aks create by hand and nobody quite remembering what flags they used. Second, and bigger: the team lead asked, in his words, whether we could "remove the dependency on ACR and AKS" — meaning, stop being tied to Azure's own Kubernetes product specifically, not just Azure in general.

Chapter 2 — What "vendor lock-in" actually means here
MAYA

That's the phrase I keep hearing and nodding along to. What does vendor lock-in actually mean, in terms anyone could picture?

DEV

It means: if we wanted to leave Azure tomorrow — move to AWS, Google Cloud, a rack in someone's office — how much would we have to rewrite? If the answer is "basically everything," you're locked in. If the answer is "just the bit that talks to the cloud," you're not, really.

The trap is usually the convenient stuff. A managed database with automatic backups, a managed message queue, a managed dashboard tool — each one removes work today, and each one is a piece of your system that only exists on that one cloud. Do enough of that and switching clouds stops being a project and becomes a rewrite.

MAYA

So had we done that? Was PCDF full of Azure-only pieces?

DEV

Actually — no, and this is the part that made the whole conversation easier than it could've been. Whoever set up the Kubernetes side originally was deliberate about it. Postgres, Kafka, Prometheus, Grafana — all of it ran as perfectly ordinary containers inside the cluster, the same containers Docker Compose already used locally. No managed Azure database, no managed Azure message queue.

There's an old design decision on file about exactly this — it says, more or less, "the cloud supplies a Kubernetes cluster and a place to store container images, and nothing above that line is bought from one vendor." Everything Azure-specific lived in one small folder, clearly labeled as the only place in the whole codebase that knew Azure existed.

MAYA

Okay, so if that was already true — what was actually still Azure-shaped?

DEV

Exactly two things: the cluster itself was AKS, and the image storage was ACR. Small, but real — both are Azure products with Azure APIs, not something every cloud offers in an identical shape. That's what the team lead was pointing at.

Chapter 3 — Terraform first: writing it down properly
MAYA

Let's do this in order. First move was Terraform, right — what problem does that actually solve?

DEV

Before Terraform, the cluster got created by running a shell script that called Azure's command-line tool directly — az aks create, az acr create, that kind of thing. It was a careful script, it even checked quota and asked "are you sure, this costs money" before doing anything. But it was still imperative — a list of steps someone runs once, by hand.

The problem with that: there's no file anywhere that says what the cluster actually looks like right now. If two people ran it with slightly different settings on two different days, you'd have two different clusters and no diff to compare them by.

MAYA

And Terraform fixes that how?

DEV

Terraform is declarative — you write a file that says "this is what should exist," and it figures out what to create, change, or delete to make reality match the file. That file lives in version control, same as application code. Anyone can read it and know exactly what's running, and before it changes anything, it shows you a plan — "here's what I'm about to do" — so nothing happens as a surprise.

MAYA

Elad also said something about "two worker nodes, one master node." What does that mean in Kubernetes terms?

DEV

That phrase is actually a small clue about what he was picturing. A Kubernetes cluster has a "control plane" — the brain that decides where things run — and "worker nodes," the machines that actually run your containers. On AKS, the control plane is invisible; Azure runs it for you and you never see a "master node" at all, you only pick how many worker nodes you want.

So "one master, two workers" isn't really AKS language — it's the language of running Kubernetes yourself, where you do stand up a visible master node. Which turned out to matter a lot for what came next.

Chapter 4 — The bigger ask: no more AKS, no more ACR
MAYA

Okay so that first Terraform version — did it still use AKS underneath?

DEV

It did, at first — Terraform that provisioned an AKS cluster and an ACR registry, just written down properly instead of run by hand. That was a real improvement on its own. But then the team lead's actual question came back around: can we drop AKS and ACR entirely, not just manage them better?

MAYA

Is that even possible? I thought Kubernetes basically needed a cloud to run it for you.

DEV

No — that's the managed-service pitch, but it's not actually true. Kubernetes is open-source software. You can install it on any Linux machine yourself. AKS just does that installation and upkeep for you, as a paid convenience.

There's a lightweight distribution called k3s that makes self-installing much less painful than it sounds — it's the same real Kubernetes API underneath, just packaged as a single small binary. One command installs it as the "server" (that's your master), and a similar one-liner joins any other machine as an "agent" (a worker).

MAYA

So the plan became: rent plain virtual machines instead of AKS, and put k3s on them ourselves?

DEV

Exactly. Three virtual machines — one running as the k3s server (the "1 master" from Elad's ask), two joined as agents (the "2 workers"). Terraform provisions plain Azure VMs now, instead of an AKS cluster. A virtual machine is about the least Azure-specific thing you can rent — literally every cloud, and plenty of on-prem racks, sell "a Linux box," so that's a much smaller thing to be tied to than "Azure's specific Kubernetes product."

MAYA

And ACR — what replaced that?

DEV

ghcr.io — GitHub's container registry. It's not Azure, it's not tied to this cloud or that one, and since we already have a GitHub org, there's no new account or billing relationship to set up. Same idea as ACR — "somewhere to store the built application images" — just not owned by the same company that owns the VMs.

Chapter 5 — What we gave up to get there
MAYA

This all sounds like a clean upgrade so far. Was there a catch?

DEV

There's a real one, and it's worth saying plainly rather than glossing over: AKS wasn't just "a Kubernetes cluster," it was a Kubernetes cluster that Microsoft keeps healthy for you. It patches the control plane, it takes care of certificates quietly expiring, it handles the version upgrades, it keeps backups of the cluster's internal state.

The moment we run k3s on our own VMs, every one of those becomes our job. Nobody's coming to fix it for us if the one server node has a bad night.

MAYA

That sounds like a lot to take on for the sake of a principle.

DEV

It's a real trade, not a free lunch — full portability against zero operational safety net. For a team that's small or stretched, staying on AKS and eating the small lock-in is a completely defensible choice. It came down to what the team actually wants to own. Given the ask, we went with dropping AKS — but it's the kind of decision worth someone consciously signing off on, not something to slide into by default.

MAYA

Anything else that broke by making this move?

DEV

One more real one — storage. AKS came with "Azure Files," a managed network drive two pods could both write to at once, which this system genuinely needs (the file-watcher and the upload form both write into the same folder). With no AKS, there's no Azure Files. So now the cluster runs its own tiny file-server pod using plain NFS — the decades-old "network file system" protocol — and everything else points at that instead. One more thing we own that we didn't used to.

Chapter 6 — Actually building it
MAYA

Alright, walk me through what actually happened when this got built for real.

DEV

First surprise: there was already an AKS cluster sitting there from an earlier trial run, still turned on, still costing money. Before touching anything new, that had to go — the old cluster and the old registry, deleted cleanly, in one shot by removing the resource group that held both.

MAYA

Bit nerve-wracking, deleting something that was actually running?

DEV

Worth checking first, always — you look at what's actually in there before you delete anything, and you get an explicit "yes, go ahead" before it happens. In this case it was clearly the leftover from the earlier AKS trial, nothing anyone was relying on, so the answer was easy. But that check happens every time, not just when it's obviously safe.

MAYA

Okay, clean slate. Then what?

DEV

Terraform needs somewhere to keep track of what it's created — its "state." So a small one-time step first: a storage account just for that bookkeeping. Then the real plan: one resource group, a network, three virtual machines — one master, two workers, matching the ask exactly.

Terraform showed the plan, it got a genuine go-ahead — this spends real money the moment it runs — and it started creating things.

MAYA

And it just... worked?

DEV

The master came up fine. Both workers failed — Azure said no, this subscription has a hard cap of 4 vCPUs total in that region, and the master alone had already used all four. Trial-subscription limit, not a mistake in the plan.

MAYA

So — request more quota?

DEV

That's the real fix eventually, and it's still sitting there as a next step. For right now, the pragmatic move: tear down the half-finished attempt cleanly, and re-apply asking for zero worker nodes — just the one server VM. k3s doesn't wall off its own server node from running workloads the way a "real" managed cluster's control plane usually does, so one machine can still run the entire stack. Not the shape that was asked for, but a working cluster today instead of a stuck one waiting on a support ticket.

Chapter 7 — Three bugs that only showed up by actually deploying
MAYA

You mentioned things broke along the way that had nothing to do with quota. What kind of things?

DEV

Three, all in the storage piece — that little file-server we built to replace Azure Files. Each one only shows up once you actually try to use the thing for real, which is exactly why standing it up and testing it mattered more than just writing the Terraform and calling it done.

MAYA

Go through them — in plain terms, please.

DEV

One — the VM couldn't speak NFS at all. Mounting a network drive needs a small helper program installed on the machine doing the mounting, and the base Ubuntu image we used doesn't include it. Like trying to open a file type your computer has no app for — the file's fine, you're just missing the program that knows how to open it. One package install fixed it, and it's now baked into the setup scripts so it happens automatically next time.

MAYA

Okay, and the second?

DEV

Two — the address didn't resolve where it needed to. Inside the cluster, our little file-server has a friendly name, like a hostname. But the actual mounting of the network drive happens a level below the cluster, directly on the virtual machine's own operating system — and that layer has never heard of the cluster's internal naming system, so the friendly name meant nothing to it. Silence, not an error — just hung forever.

Fix: give that file-server a fixed, unchanging numeric address instead of relying on the name, and point the mount at the number directly. Less friendly to read, completely unambiguous to use.

MAYA

And the third?

DEV

Three — asking for the wrong folder. This one's a bit odd but harmless once you know it: the little file-server software we used has a setting that makes its shared folder become the very top of what it offers, rather than a folder inside the top. We were asking for "the folder named exports," when what actually existed at that point was just "everything," full stop — so the server correctly said "no such folder," because from its point of view, that name didn't exist as a sub-folder anymore. Pointing at the top level instead of the named folder fixed it immediately.

MAYA

That's three separate, fiddly things. How'd you even track them down?

DEV

One at a time, in order — fix one, watch what happens, read the next error, fix that. Each one produced a different, specific error message once the previous one was out of the way, which made them findable rather than mysterious. That's really the whole method: change the smallest thing that could be wrong, look again, repeat.

Chapter 8 — Getting images onto the cluster
MAYA

Before the storage saga — where did the actual application come from? The cluster doesn't run source code directly, right?

DEV

Right — everything gets built into a container image first, one per service, eight in total. There's already a script that does exactly this and pushes the result somewhere; it never cared which registry, so pointing it at ghcr.io instead of ACR was a one-line change, not a rewrite.

MAYA

And then the cluster just... pulls them?

DEV

Almost — this is where ACR's convenience quietly showed up again. AKS could be told "trust this registry," once, and every pod could pull from it with no further setup. ghcr.io has no equivalent handshake with a cluster it's never heard of, so the cluster needs its own credential — a small secret holding a username and an access token, referenced by every workload that needs to pull one of our private images.

That secret should never just get typed into a chat window or a shared log — it's a real, live credential. It got created directly against the cluster instead, and flagged for rotating afterwards the moment it did end up pasted somewhere it shouldn't have.

Chapter 9 — Proving it actually works
MAYA

Okay, so eventually every pod said "Running." Done?

DEV

"Running" only proves the containers started — it says nothing about whether the actual pipeline logic works end to end. So the real test: build a tiny fake vendor file, three made-up companies, and push it through the front door exactly the way a real vendor export would arrive.

MAYA

What did that look like?

DEV

A three-row CSV — company name, website, city, country, phone, employee count — dropped into the folder the watcher polls. Within one polling cycle, the watcher's log said it plainly: read 3, processed 3, failed 0, new 3. It had even worked out what the six column headers meant on its own, with no manual mapping written for this made-up vendor.

Then the real proof — querying the database directly for finished "golden records," the very last stage of the pipeline — and there they were. All three companies, every field correct, having survived ingestion, mapping, normalization, validation, and matching, in that order, for real.

MAYA

That's a genuinely reassuring thing to see, not just "the pods are green."

DEV

Exactly the point of doing it. A healthy-looking pod and a working pipeline are two different claims, and only one of them was actually tested until that step.

MAYA

Last thing — how do I actually go look at it myself?

DEV

Two commands, and it stays entirely on your own machine — nothing gets exposed to the internet by running these.

See it yourself

Review console
kubectl port-forward -n pcdf svc/review-console 8000:8000
then open http://localhost:8000/admin/page
Dashboards
kubectl port-forward -n pcdf svc/grafana 3000:3000
Login keys
kubectl get secret pcdf-secrets -n pcdf -o jsonpath='{.data.pcdf_api_keys}' | base64 -d

Leave the port-forward running in its own window while you're looking — close it and the tunnel closes, the console keeps running on the cluster either way.

MAYA

Alright. That actually all makes sense now — thanks for walking through it properly instead of just handing me "it's done."

DEV

That's the part worth remembering more than any of the specific fixes: "it's done" and "it's been proven to work" are different sentences. Worth keeping them different.
