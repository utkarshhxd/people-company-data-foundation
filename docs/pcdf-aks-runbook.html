The People & Company Data Foundation (PCDF) — a Postgres/Kafka pipeline that already ran on Docker Compose — now runs the same way on Azure Kubernetes Service. Every piece is a pod. Nothing is Azure's except the cluster and the registry it pulls images from.

Where things stand right now: the AKS node is stopped — compute billing is off. Every disk, every database row, every manifest survives untouched. az aks start --name pcdf-aks --resource-group pcdf brings it back exactly as it was, in 2–5 minutes, no redeploy. See §12.

02

Starting point

Before any of this, PCDF already worked — on one machine, via Docker Compose.

The repository turns messy vendor exports of people and companies into deduplicated, provenance-tracked "golden records." It's eleven services deep: Postgres holds the truth, Kafka announces when a batch is ready, five stage consumers (mapping → normalization → validation → resolution → golden) carry a record from raw row to trusted value, a watcher drives files dropped into a folder through the whole thing automatically, and a review console gives a human the four queues that need a decision.

A partial Kubernetes translation already existed — seven files under infra/k8s/base/ — but its own README said it plainly: "written and rendered, not deployed." It covered three of the eleven running pieces (Postgres, the migrate Job, the watcher) and an ADR on file (0016) claimed a three-broker Kafka cluster and ten Deployments that simply weren't on disk. Nobody had ever pointed a real cluster at it.

03

The big call: pods, not managed services

Azure sells a managed Postgres with point-in-time restore and a managed Kafka-compatible broker. The question that decided everything downstream: buy those, or run everything ourselves inside the cluster?

Decision

Everything runs as a pod. Azure supplies exactly two things: a Kubernetes cluster and a container registry.

Postgres, Kafka, Prometheus, Alertmanager and Grafana are containers in the cluster, exactly as they're containers under Compose. Nothing in infra/ names Azure. The only directory in the entire repository that knows the cloud provider exists is deploy/azure/ — and that's on purpose.

This was the user's explicit steer, verbatim: "we need to independ of these cloud providers, we dont need to get vender loced in." That one sentence ruled out Azure Database for PostgreSQL and Azure Event Hubs before any cost comparison mattered — but the cost comparison backs it up anyway.

Self-hosted on k8s — chosen
  • Runs identically on AKS, GKE, EKS, or a rack in a closet — same YAML, one overlay swap
  • Same Dockerfiles Compose already builds; nothing forked into a cloud-only variant
  • Matches the project's own design premise (ADR 0003 / 0020): the data is meant to outlive whatever displays it — a pipeline that can't be moved contradicts that
  • az aks stop parks the whole stack at near-zero cost between sessions — a managed database has no equivalent pause button
Self-hosted on k8s — the price paid
  • We own Postgres backup, patching, and failover — nobody else's product does it for us
  • No automatic point-in-time restore; the nightly pg_dump CronJob is the whole safety net
  • More manifests to write and maintain by hand
  • Every rough edge is ours to hit — and we hit six of them (see §08)
Managed Azure services — rejected
  • Azure Event Hubs' Kafka endpoint is SASL_SSL only — every consumer here assumes PLAINTEXT, so switching later is a real code change disguised as a config change
  • Real lock-in: leaving Azure later means rewriting the client, not re-pointing a hostname
  • Flexible Server has no cheap "off" switch the way an AKS node pool does — it bills continuously
  • Contradicts the "data outlives the display app" premise the rest of the codebase already commits to
Managed Azure services — what they'd have bought
  • Automatic backups, patching, and point-in-time restore — solved problems, not owned ones
  • An HA option for Postgres without hand-building Patroni or CloudNativePG
  • Less YAML overall; less to go wrong on a bad Tuesday
  • Battle-tested at a scale this project isn't at yet
Verdict: the trade was accepted with eyes open. Postgres failover still doesn't exist here — that gap is real and documented, not hidden — but it's a gap that can be closed later (streaming replication, a managed tier, whatever) without anyone having rewritten application code to get there.
04

Three layers, one Azure-shaped seam

Kustomize overlays, not Helm — every other config surface in this repo is plain YAML, and a chart would be the first templating layer in the project.

LayerKnows aboutJob
infra/k8s/base/Nothing cloud-specificThe whole stack, portable. Every Deployment, StatefulSet, Service, PVC, CronJob.
deploy/azure/AzureTwo edits only: the ACR registry each image resolves to, and azurefile-csi as the ReadWriteMany class for the shared /data volume.
deploy/azure-trial/Azure + a 4-vCPU quotaLayers on top of deploy/azure: drops the shared volume back to ReadWriteOnce (one node makes RWX unnecessary), adds CPU/memory requests to all 14 workloads so a 16 GiB node doesn't starve itself.

Why deploy/ and not infra/overlays/azure/, which is where you'd expect it: kustomize refuses a base that contains the overlay pointing back at it — "cycle detected." The base's root has to stay infra/ so it can read the Prometheus rules and Grafana dashboards underneath it, so the overlay had to move out.

What this buys, concretely: moving to GKE tomorrow means copying deploy/azure/, changing a registry hostname and a storage-class name, and nothing else. No application code, no Dockerfile, no base manifest touches Azure at all.

06

The money problem

Free-trial credit, a stray college-project VM already burning it, and a 4-vCPU wall in the region I picked first.

The typo that mattered

The plan changed twice on one number. First: "i think we have 16 left" — read as ₹16, which would buy under half an hour against a two-node default. Then the correction: ₹16,000 — the standard Azure free-trial grant. Both readings had to be taken seriously in the moment; only one turned out true, and the whole sizing plan below is built for it.

An old VM was already spending it

Before creating anything, a full resource inventory turned up something unexpected: web-server-vm, a Standard_B2as_v2 instance in resource group azure-mini-project-rg, running continuously since 2026-08-06 — nineteen days — with a static public IP and a Premium_LRS disk attached. A leftover from an earlier college project, still billing.

Asked directly — deallocate (reversible, keeps the disk) or delete the whole resource group (permanent) — the answer was delete. az group delete --name azure-mini-project-rg --yes removed the VM, its disk, its static IP, its network, everything. The region's vCPU usage measured 2 used before, 0 after: confirmation the deletion actually freed the quota it was consuming, independent of exactly which metadata field said which region.

The 4-vCPU wall

Every Azure free-trial subscription caps regional vCPU quota at 4. That number decided the node size before anything else did.

RegionQuota (used/limit)4-vCPU general-purpose sizes available
centralindia0/4 (after cleanup)None — D4s_v5 and D4as_v5 both flagged NotAvailableForSubscription; only confidential-compute and GPU sizes were unrestricted
eastus0/4Standard_D4s_v7 — 4 vCPU / 16 GiB, unrestricted, 12 attachable disks
southindia0/4Standard_D4as_v5 and several others, all unrestricted — chosen, 8 attachable disks

southindia won over eastus for one reason beyond availability: it keeps the data in India. The stack claims exactly 7 PersistentVolumeClaims against that size's 8-disk ceiling — comfortable, but the note is now in two files so nobody adds an eighth stateful thing without counting first.

Sizing the single node

One node instead of two smaller ones, deliberately: two nodes waste more of the total on kubelet/system overhead, 16 GiB in one place beats an 8+8 split for Kafka and Prometheus specifically, and — the real payoff — a single node makes the shared-volume problem disappear. Both pods that write /data (the watcher and the console's upload handler) land on the same node by definition, so the ReadWriteMany requirement, and Azure Files with it, was never actually needed. deploy/azure-trial patches the volume back to ReadWriteOnce on the plain managed-csi disk class.

Single node — what it bought
  • Fits the 4-vCPU quota exactly, no waiting on a quota increase
  • ReadWriteOnce works — one fewer unverified storage path
  • Fully provable at close to zero infra spend beyond the node itself
  • az aks stop cleanly parks it between sessions
Single node — what it costs
  • Zero high availability — a node reboot is a full outage
  • Never exercises the ReadWriteMany path a real multi-node deploy needs
  • Only 1 of 8 disk slots spare
  • Requests were sized tight: 1,850m CPU / 4.4 GiB against ~3,860m / ~11.5 GiB allocatable
07

Standing it up

The script worked — but the first run aborted itself, and the reason is worth keeping.

A script that looked hung wasn't

The first live run of deploy/azure/create-cluster.sh sat silent for over two minutes on an az vm list-skus call — downloading roughly 750 VM sizes to confirm the requested one was actually offered. With no progress output, that silence read as a hang. Keystrokes typed into the wait — the pcdf confirmation, typed early — sat buffered in the terminal. When the real prompt finally appeared, it consumed a stray blank line first, didn't match, and aborted with nothing created; the leftover pcdf then landed on the shell as a bogus command.

Measured directly: that one call took 136.6 seconds, consistently. The fix wasn't to make it faster — it's an Azure API, not ours to speed up — it was to stop pretending the wait wasn't happening.

08

What actually exists in Azure

Fourteen real objects, sitting in two resource groups — not one. Every single thing that was created, and the plain reason each one is there.

i
Pulled directly from the live subscription while writing this section — not recalled from memory. az resource list, run twice, against both resource groups.

The resource group holds less than you'd expect

Open the Azure Portal and look inside pcdf — the one resource group this project asked for by name — and exactly two things are in it: the AKS cluster object, and the container registry. That's the whole list.

Everything the cluster actually needs to run — the virtual machine, its disks, the network, the load balancer, the identity that lets it pull images — lives in a second resource group Azure created on its own and named itself: MC_pcdf_pcdf-aks_southindia ("MC" for managed cluster). This isn't something asked for, and it isn't unique to this project — every AKS cluster on every Azure subscription does this. The split is deliberate: pcdf is the thing managed directly — start it, stop it, delete it, resize it. MC_... is Azure's own workshop, rebuilt automatically any time the cluster's shape changes, and not meant to be edited by hand.

!
Why this matters for the bill: deleting only pcdf — without knowing the second group exists — is a common way people think they've cleaned up and haven't. The good news: az group delete --name pcdf --yes already does the right thing. Deleting the AKS cluster object triggers Azure to tear down the entire MC_... group behind it automatically. One command, both groups gone — but it's worth knowing where the second one is, since nearly everything in the cost table further down actually lives there.

The simplest way to picture it

Think of it as a small rented office rather than a server. pcdf is the lease and the sign by the front desk — the thing with a name on it. MC_pcdf_pcdf-aks_southindia is the actual room Azure built inside that building: one desk (the node) doing the real work, seven filing cabinets (the disks) holding what has to survive even if the desk gets cleared out, a supply closet down the hall (the registry) stocked with pre-built shipping containers (the 8 images) the desk pulls from whenever it needs to set something up, a front door with a mail slot (the load balancer and its IP) so traffic can get in and out, and an ID badge (the managed identity) that lets the desk walk into that supply closet without anyone having to cut it a key.

Stopping the cluster is like sending the one person at that desk home for the night. The room, the filing cabinets, the mail slot, and the supply closet all stay exactly as they were — and every one of them keeps costing something small, every single day, whether anyone's sitting at the desk or not.

09

Six bugs, six fixes

Every one of these surfaced only once real pods hit real Azure infrastructure — no amount of rendering the YAML would have caught them. None is Azure-specific; every one would break identically on any Kubernetes cluster.

1The secret mount blocked Kubernetes' own service-account token
Symptom
mkdirat ... read-only file system — every pod mounting a secret died before any application code ran
Root cause
The secret volume mounts at /run/secrets. On Linux, /var/run is a symlink to /run. Kubernetes tries to auto-mount its service-account token at /var/run/secrets/kubernetes.io/serviceaccount — which meant creating a directory inside a mount already marked read-only. It couldn't.
Fix
automountServiceAccountToken: false, added to 9 manifests. Correct on its own terms too — nothing in this stack calls the Kubernetes API.
Why it's not Azure-specific
Pure Linux path-symlink mechanics. Identical on any distro, any cluster.
2Kafka refused to start on lost+found
Symptom
Found directory /var/lib/kafka/data/lost+found ... should only contain Kafka topic data — fatal, broker exits immediately
Root cause
A PersistentVolume arrives as a freshly formatted ext4 filesystem, and every ext4 volume has a lost+found directory at its root. Kafka demands its log directory contain nothing but topic-partition data.
Fix
KAFKA_LOG_DIRS pointed at a subdirectory of the mount instead of the mount root.
Why it's not Azure-specific
Docker Compose never hit this because a bind-mounted volume is a directory on an already-formatted host filesystem, not a fresh one. Any cloud's block storage formats the same way.
3Kafka couldn't resolve its own controller — twice
Symptom
java.net.UnknownHostException: kafka-0.kafka: Name does not resolve
Root cause (part one)
KAFKA_CONTROLLER_QUORUM_VOTERS names the broker as kafka-0.kafka — a per-pod DNS name that only exists when the governing Service is headless. It was a plain ClusterIP Service.
Root cause (part two)
Making it headless exposed a deadlock: a headless Service publishes DNS only for pods already marked Ready — and the broker can't become Ready until it resolves its own controller address.
Fix
clusterIP: None plus publishNotReadyAddresses: true. Safe here specifically because there's one broker — "an address that might not be ready" is the only address there is.
Why it's not Azure-specific
Pure Kubernetes DNS/Service semantics, identical on every distribution.
4The migrate Job gave up too early
Symptom
Job status permanently Failed — required manual delete and recreate before it would try again
Root cause
backoffLimit: 3 expires roughly a minute in. On a cold cluster, that's exactly the window where Postgres is still attaching its disk and running initdb — so the "database not reachable yet" case, which is normal, was being treated as permanent failure.
Fix
Raised to backoffLimit: 10. Costs nothing when the schema's already current — the first attempt just succeeds.
Why it's not Azure-specific
Any cold Kubernetes cluster races a dependent Job against a StatefulSet's first boot the same way.
5The shared data volume was unwritable
Symptom
mkdir: cannot access '/data/inbox': Permission denied — the watcher couldn't create the directory it exists to watch
Root cause
Every image here runs as non-root uid 10001. A fresh PersistentVolume arrives owned by root.
Fix
securityContext.fsGroup: 10001 on the watcher and console pod specs — the kubelet then hands the volume over group-writable.
Why it's not Azure-specific
Docker Compose never hit this either — a bind mount inherits the ownership of a host directory the developer already owns.
6A carriage return hid inside the Postgres password
Symptom
The backup CronJob failed with password authentication failed for user "pcdf_dev" — while the application connected to the exact same database with the exact same password, successfully, the whole time
Root cause
openssl rand on Git Bash / MSYS emits CRLF line endings, not LF. tr -d '\n' stripped the newline but left the carriage return sitting inside the value — a 33-byte password where 32 was intended. Postgres initialized with that byte baked in via the mounted file; the application read the identical file and matched perfectly. Only the backup Job, which receives the value through an environment variable instead of reading the file, disagreed.
Fix
Regenerated every credential with tr -d '\r\n', confirmed clean with od -c, applied the new password with ALTER USER directly against Postgres, replaced the Kubernetes Secret, restarted every pod that reads it.
Why it's not Azure-specific
A Windows-shell quirk in credential generation, not a cluster issue at all — but the one bug here that stayed silent longest, because the "obvious" check (does the app connect?) said everything was fine.

11

Two credentials that don't rotate the easy way

Changing the Kubernetes Secret is not the same as changing the password — for exactly two components, and for the same underlying reason.

!
Both Postgres and Grafana read their admin credential from the environment only once — the moment they first initialize their own storage. After that, the credential lives inside their own database, and a changed Secret is silently ignored.

Postgres

POSTGRES_PASSWORD_FILE is read only during initdb, on the very first start against an empty volume. Rotating it afterward means going through Postgres itself:

# set the new password inside the database
kubectl exec -n pcdf postgres-0 -- psql -U pcdf_dev -d pcdf \
  -c "ALTER USER pcdf_dev PASSWORD 'the-new-value';"

# then update the Secret to match, and restart everything that reads it
kubectl rollout restart deploy -n pcdf

Grafana

GF_SECURITY_ADMIN_PASSWORD is read only when Grafana first creates grafana.db on its volume. The symptom is deceptively clean: "Invalid username or password," while holding what is demonstrably the correct value.

GP=$(kubectl get pod -n pcdf -l app=grafana -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n pcdf "$GP" -- grafana cli --homepath /usr/share/grafana \
  admin reset-admin-password 'the-new-value'
Admin password changed successfully ✔

Everything else — the five consumers, the watcher, the console — has no such quirk: they read the mounted secret file fresh at every startup, so a plain restart is all any of them need.

Getting data out

Five tested queries live in tools/sql/companies.sql. The one trap that will silently give wrong answers if missed:

!
golden_attribute keeps every value it ever chose — superseded rows stay in the table rather than being deleted. Every query needs WHERE valid_to IS NULL, or the "current" value and its whole history come back mixed together.

Companies as a flat table

SELECT
    MAX(g.value) FILTER (WHERE g.canonical_field = 'company_name')   AS company_name,
    MAX(g.value) FILTER (WHERE g.canonical_field = 'website')        AS website,
    MAX(g.value) FILTER (WHERE g.canonical_field = 'industry')       AS industry,
    MAX(g.value) FILTER (WHERE g.canonical_field = 'city')           AS city,
    MAX(g.value) FILTER (WHERE g.canonical_field = 'country')        AS country,
    MAX(g.value) FILTER (WHERE g.canonical_field = 'employee_count') AS employee_count
FROM entity e
JOIN golden_attribute g ON g.entity_id = e.entity_id AND g.valid_to IS NULL
WHERE e.entity_type = 'company' AND e.status = 'active'
GROUP BY e.entity_id
ORDER BY company_name
LIMIT 50;

Run the whole reference file

kubectl exec -i -n pcdf postgres-0 -- psql -U pcdf_dev -d pcdf < tools/sql/companies.sql

Where it stands right now

Stopped, not deleted — a deliberate choice between two real options.

Stop — chosen
  • Compute billing drops to zero within minutes
  • All 816 entities, every fix, every manifest survives untouched
  • az aks start returns to exactly this state in 2–5 minutes — no redeploy
  • Residual cost stays small: disks + registry only
Delete — the alternative
  • Zero cost, full stop, nothing left to forget about
  • Loses all 816 resolved entities immediately
  • Every one of the six bugs would have to be re-discovered live next time — the fixes live in the manifests now, so it's a repeat run, not repeat debugging, but still a from-scratch cluster

Cost while stopped

Node compute is the only thing az aks stop actually switches off — from ~₹14/hr down to ₹0. Everything else that was created keeps existing and keeps billing at a small, steady rate: the seven data disks, the node's own 128 GiB disk, the load balancer's static IP, and the registry. §08 has the full object-by-object breakdown and the reasoning behind each line; the total lands around ₹1,800–2,200/month while parked exactly like this.

What's not proven

Everything above is real and tested. This is what wasn't — stated plainly, on purpose.

  • No high availability, anywhere. One node means a reboot is a full outage. Postgres is a single instance with no standby; real failover needs streaming replication (Patroni, CloudNativePG), and that's not built.
  • ReadWriteMany was never exercised. The trial overlay deliberately bypasses it by keeping both writer pods on one node. A real multi-node deployment needs that path proven separately.
  • The backup CronJob has only run on demand. It's fired manually twice, successfully, but never yet on its actual 02:00 UTC schedule unattended.
  • No public Ingress is applied. The console is reachable only through kubectl port-forward, which is deliberate — it holds personal data with full provenance, and the Ingress template needs a real hostname and certificate issuer before it's safe to apply.
  • Image builds still happen on a local machine. docker build runs locally, then pushes to ACR — a rebuild needs this machine specifically, unless that step moves to az acr build later.
