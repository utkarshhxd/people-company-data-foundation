01 · Read this first

The mental model

This system is an evidence-preserving data pipeline. It never treats a cleaned value, a match score, or an AI answer as unquestionable truth. It stores what a source said, records each later judgement separately, and only then derives a trusted view.

Evidence

raw_record and attribute_observation.raw_value preserve the source row and cell. They are the audit foundation.

Judgements

Mappings, validation results, match decisions, and survivorship choices are stored beside the evidence, never folded into one opaque score.

Uncertainty

Ambiguous mappings, possible duplicates, invalid rows, and AI guesses go to review queues. The pipeline prefers “ask” over “invent.”

Derived truth

golden_attribute is computed from linked observations. It can be rebuilt; it is never the only copy of a fact.

The ten load-bearing rules

  1. Keep the original. Raw values are stored before they are interpreted; normalization never edits them.
  2. One bad row costs one row. In the record-at-a-time path, a failed record is rolled back, written to record_error, and the next row continues.
  3. Postgres is the source of truth. Kafka messages carry identifiers and counts, never source payloads.
  4. Only confirmed mappings become canonical. A needs_review guess is stored but cannot validate, resolve, or become golden data.
  5. Warnings do not condemn a record. Only record-level error rules make a row invalid; an unusable phone does not erase a valid person.
  6. Weak identity signals cannot add up to certainty. Moderate resolution keys are hard-capped below automatic linking.
  7. Human uncertainty is durable. Review queues live in Postgres; they do not disappear on restart or time out.
  8. Entity IDs remain resolvable. A merge turns the absorbed entity into a tombstone pointing to the survivor instead of deleting it.
  9. Golden history is temporal. Rebuilding the same answer does not reset valid_from; a changed answer closes the old row.
  10. AI may propose, never assert. AI output becomes evidence only after a human accepts it, through a low-reliability synthetic source.
Five numbers that must never be added together: mapping confidence, validation outcome, source reliability, match confidence, and golden-value confidence answer different questions. The provenance code deliberately shows them side by side.
02 · System view

Architecture: evidence in the center

There are two ways to run the same stage logic. Watched/manual “process” loads run a record all the way through in one transaction. Raw batch ingestion announces committed work to five long-running consumers. Both paths call the same mapping, normalization, validation, resolution, and golden functions.

Storage

PostgreSQL stores both immutable evidence and recomputable state. Twenty-five ordered migrations define the schema.

Notification

Kafka has three partitions per topic and replication factor one. Consumers commit offsets only after successful work.

Interaction

A FastAPI service exposes the admin/review UI, JSON endpoints, Server-Sent Events, Prometheus metrics, and health checks.

Watched-feed logic, step by step

  1. discover_feeds() scans one directory level and validates each feed.json. A broken feed produces a warning without stopping other feeds.
  2. candidate_files() ignores configuration, hidden files, and temporary/receipt suffixes (.log, .json, .tmp, .part, .crdownload, .swp); candidates are processed oldest-modified first.
  3. Watcher._settled() compares a file’s size and modification time across two complete polls. The first sighting records a fingerprint; only an unchanged second sighting is safe to load.
  4. Before a sweep, the watcher reads both ingestion and validation control states. If either is paused, files stay exactly where they are.
  5. process_file() calls the record-at-a-time runner with the feed’s stable arguments.
  6. A successful file moves to _done with a timestamp and receipt. A read/run failure moves to _failed with the reason. A content duplicate moves to _done, because there is no defective file to investigate.
  7. The watcher beats after each sweep and after each processed file, so a long backlog still looks alive.
Why the settle test matters: a CSV still being copied is a syntactically valid truncated file. Reading it early can silently omit every row after the current byte, which is more dangerous than a loud parse failure.

Durable browser-upload queue

  • A PostgreSQL advisory lock (CLAIM_LOCK) serializes the short claim transaction; row selection also uses FOR UPDATE SKIP LOCKED. The lock is released before ingestion, so global one-file-at-a-time behavior requires one active worker replica.
  • A running item updates heartbeat_at every 20 seconds. If it has been silent for 180 seconds, the next sweep returns it to queued.
  • When ingestion is paused, all waiting rows become held. They return to queued when ingestion resumes.
  • Only waiting items can be cancelled. A running batch is not interrupted, because stopping halfway requires explicit batch-abandon semantics.
  • Finished or cancelled items can be requeued without uploading the bytes again; their attempt counter remains visible.
  • The worker calls ingestion.pipeline.ingest(), so admin uploads enter the batch/Kafka path.
06 · Phase 1

Ingestion: preserve what the source said

Ingestion deliberately interprets as little as possible. It establishes source and batch identity, reads every usable row as strings, stores the original payload, and only then announces that a completed batch exists.

Reader behavior

CaseLogicReason
CSV / TSV / TXTRead lazily in chunks; default batch size 5,000; disable type inference; strip UTF-8 BOM from the header.Peak memory stays bounded and strings such as 00501 survive.
ExcelRead one selected sheet fully through Calamine, then yield write batches.XLSX is a compressed archive; the current reader cannot stream individual rows.

Duplicate headersname, name__2, name__3.Both columns remain addressable and deterministic.
Blank headerRename to unnamed, with suffixes if repeated.A value must not vanish because its header was empty.
Completely empty rowDrop it before persistence.It carries no observation; placeholder strings such as N/A are not considered empty here.
Ragged linesDo not truncate them.A malformed row should fail loudly rather than lose trailing cells.

Batch-ingestion algorithm

  1. Fingerprint bytes. Stream the file through SHA-256 in 1 MiB chunks and capture its size.
  2. Guard the intake gate. control.guard(conn, "ingestion") runs before a source or batch is created.
  3. Resolve source identity. Create or reuse the named source and persist reliability plus optional describes semantics.
  4. Apply duplicate policy. Same hash + same source + completed is blocked unless allow_reingest; same file currently in flight is always blocked; same bytes under another source warn and continue.
  5. Create a running batch. Store file path/name/hash/size/entity type. On the first chunk, store the ordered column list because JSONB does not preserve source key order as a layout contract.
  6. Write raw rows. Use the named record-ID column when populated; otherwise use the global row number. Each row also gets a deterministic payload hash.
  7. Commit each chunk. Partial rows remain if a later chunk fails, but the batch becomes failed, so downstream stages reject it as inert.
  8. Finish, then announce. Mark the batch completed, commit, publish pcdf.batch.ingested, and record events_published_at only after delivery succeeds.

Publish failure

The load is still successful because the rows and completed batch already exist. The error is logged and events_published_at stays null, making the unannounced batch queryable and replayable.

Partial read/write failure

Committed rows are retained as evidence, the batch is marked failed with an error, and no completion event is emitted. Every downstream batch function requires status = completed.

Record-at-a-time differences

record_pipeline.runner.run_file() performs the same hash and duplicate checks, but then reads one row at a time. Before database work it screens only two certainly-unstorable cases: NUL bytes and unpaired Unicode surrogates. Anything else is offered to Postgres; if it fails, that row is rolled back and its parsed payload is stored both readably and as exact JSON-serialization bytes in record_error. This preserves every parsed value—including otherwise unstorable characters—but not the original CSV quoting, delimiters, or Excel cell encoding. The batch is completed only after all rows have been visited.

With --async-commit, synchronous_commit is disabled for speed. Atomicity and isolation remain, but a crash may lose a suffix of recently acknowledged records. Because the batch-complete marker is written last, such a crash leaves the batch uncompleted and therefore unusable downstream; recovery is a deliberate re-run.

Processing error is not quarantine. record_error means code, encoding, storage, or infrastructure prevented a row from completing the pipeline. Quarantine means processing succeeded and validation intentionally held the row back.

07 · Phase 2

Schema mapping: what does each column mean?

Mapping converts vendor vocabulary such as e_mail, mobile_no, or org_name into the fixed canonical schema. It makes one decision per source column—not one decision per cell.

Mapping identity and reuse

  • A layout is identified by source ID + ordered-column fingerprint + canonical schema version.
  • The fingerprint is a SHA-256 over the ordered, disambiguated source names exactly as stored. Column spelling and order are deliberately significant.
  • The canonical schema is currently version 4. A meaning-changing vocabulary edit must bump that version.
  • When a layout is already known, its existing source_schema and human overrides are reused. New derivation is skipped.
  • For a new layout, the first 200 records provide value-shape samples.

The decision pipeline for one column

Integer, year, phone, and postal detectors may corroborate a matching name but cannot originate a field proposal: their shapes are shared by too many unrelated columns. Value-only proposals are also limited to the self subject, because values cannot reveal whether a phone or URL belongs to the person or employer. Evidence retains at most the next three distinct alternatives behind the chosen candidate.

Collision resolution

Collisions are grouped by (canonical_field, subject). A person’s city and the employer’s city therefore do not collide. Evidence kinds rank as exact alias (3), corroborated (2), ambiguous/similarity (1), value/AI (0). If exactly one claimant has the best rank it keeps the field and weaker claimants become unmapped. If several share the best rank, each claimant is put into review instead of silently breaking the tie by score.

Why status matters downstream

Only auto_accepted and approved mappings set an observation’s canonical_field. A needs_review, unmapped, or rejected column is still stored in full, but it is not validated, used as an identity key, or considered by golden survivorship.
08 · Phase 3

Normalization: make values comparable, not “correct”

Normalization creates attribute observations. Its contract is lossless: every source column produces at least one observation, even when it is absent, unmapped, a known null token, multi-valued, or impossible to normalize.

How one observation is formed

  1. Look up the column mapping. Only auto_accepted and approved are confirmed.
  2. If unconfirmed, store canonical_field = NULL, subject = self, and normalize as plain text.
  3. If confirmed, obtain the field’s value_type and subject from the canonical schema.
  4. A truly missing cell still creates one observation with empty raw value, null normalized value, and method <type>:absent.
  5. Otherwise split the cell according to safe multi-value rules and normalize each piece.
  6. Persist record, batch, source, entity type, source column, canonical field, mapping status, value index, raw value, normalized value, value type, method, null flag, timestamp, and subject.

Splitting rules

  • ^^ is an explicit multi-value marker and splits every value type.
  • Semicolon and pipe split only email, phone, and url.
  • Addresses and free text never split on punctuation; commas and semicolons may be meaningful.
  • Empty pieces are removed, but a cell made only of delimiters still produces one empty observation.
  • value_index preserves the original order: 0, 1, 2, and so on.

Null and failure semantics

Conservative, case-insensitive null tokens include empty text, null, n/a, n\a, the literal marker \n, none, nil, one to three dashes, (null), not available, and unknown. The token na is intentionally not null because it can mean Namibia or North America. A normalizer exception never escapes: it produces no normalized value and method <type>:failed, leaving validation to describe the problem.

Batch persistence and reprocessing

normalize_batch() streams raw records through a server-side cursor, buffers 2,000 observations, upserts by (record_id, source_column, value_index), and commits each buffer. On a re-run the immutable raw value and observation time are not changed, while mapping attribution, normalized value, type, method, null flag, and subject are refreshed. This is what allows a newly approved mapping to reach already-stored rows.

09 · Phase 4

Validation: can this value and this row be used?

Validation attaches judgements; it never repairs a value, drops a row, or decides which source wins. Ruleset version 3 distinguishes this policy from earlier stored results.

Attribute rules versus record rules

Attribute scope

Asks whether one normalized observation can serve as its mapped field. A malformed email is an error about that value.

Record scope

Asks whether the row can identify an entity at all and whether it is legible. Only record-scope errors invalidate the entire row.

Attribute dispatch

  1. If canonical_field is null, the observation is counted as unvalidated. Testing it against a guessed field would only validate the guess.
  2. If normalized value is null, a common outcome rule converts :failed and :empty to error failures, and :range to a warning. Genuine absence/null tokens produce no judgement.
  3. Otherwise every rule registered for the observation’s value type runs.
  4. A broken rule is contained and stored as info-level rule.error; it neither crashes the batch nor pretends to pass.
  5. Passes are stored as well as failures, so “passed” is distinguishable from “never evaluated.”

10 · Phase 4b

Quarantine and the validation circuit breaker

Quarantine is a visibility gate, not a trash can. An invalid row remains in the raw and observation tables but is excluded from the resolvable_record view until its state permits use.

Pure transition rules

  • No existing item + invalid → open.
  • Open + same error reasons → no churn; changed reasons → append reasons_changed.
  • Released + same errors → reviewer’s override stands; new errors → reopen.
  • Open or released + clean revalidation → resolved automatically.
  • Resolved + later invalid → open again.
  • Rejected is terminal under automatic routing. A human must explicitly reopen it.

Validation writes the verdict, summary, quarantine item, and transition event in the same database transaction. There is never a committed moment when a record is known invalid but still appears to resolution as safe.

Circuit breaker

Signal

invalid / processed for the current run, not a lifetime count.

Defaults

Enabled, minimum 100 records, trip at 95% invalid. The top five error-rule causes become evidence.

Action

Persistently pause validation through pipeline_control. It never auto-clears; a person must resume it.

In batch mode, assessment happens after that batch’s verdicts are fully stored. In the record path, assessment runs every 200 successful records, so the earliest practical stop is row 200 even though the configured floor is 100. Already committed records keep their outcome; the rest of the file is unread and the batch is left failed/inert.

Code: validation/quarantine.py, validation/breaker.py.

11 · Phase 5

Entity resolution: deciding who is the same

Resolution turns usable source records into durable person or company entities. It is a deliberately conservative identity algorithm: exact identity keys generate candidates, weighted evidence scores them, and uncertain cases become review tasks instead of silent merges.

Current v4 key-coverage nuance: the person name_company key is defined, but company_name on a person layout belongs to the employer subject while person-key lookup reads only self. It is therefore normally absent for correctly mapped v4 rows. Phone blocking likewise reads only the generic phone field, not mobile_phone, work_phone, home_phone, other_phone, or fax_phone.

Scoring, concurrency, and the three outcomes

score = strongest matching key weight + 0.04 × additional distinct key types, capped at 0.99

If either the incoming key or stored key is moderate, that particular match is treated as moderate. A candidate whose strongest evidence is moderate is capped at .89, just below the .90 auto-link threshold. All considered key matches are stored as evidence; the decision is therefore explainable rather than just a number.

  1. Read only confirmed, non-null self observations. Employer-subject values do not identify the person.
  2. Build and sort distinct keys. The repository takes PostgreSQL advisory locks in stable order, preventing two workers from independently creating the same identity.
  3. Look up active entities that own those keys. Absorbed/tombstoned entities are not normal candidates.
  4. Score each candidate. Highest score wins; equal top scores at or above .90 are deliberately ambiguous.
  5. Write one atomic result. Auto-link attaches the row and adds keys. New creates an entity, self-link, and keys. Review also creates a separate entity and link, then records a match_candidate against the possible survivor.
Subtle but important: attribute-level validation errors do not currently remove an observation from identity-key construction. Quarantine blocks record-level invalid rows, and role-email logic demotes risky email keys, but a merely warning-status row can still contribute an attribute that has an error result. See implementation notes.

What an accepted duplicate does

Accepting a match_candidate is a merge, not just a UI flag. The code locks the candidate, follows any prior merge chain (maximum 16 hops), moves record links and identity keys to the survivor, marks the absorbed entity with its survivor pointer, writes entity_merge audit evidence, and closes the candidate. Rejecting leaves both entities separate and closes the candidate as rejected. The console then rebuilds the survivor’s golden record so the newly combined evidence is visible.

12 · Resolution sub-flow

Employer extraction from a person row

A person export can describe two real-world subjects in one row: the person and their employer. Mapping labels those employer columns with subject = employer; this sub-flow decides whether that evidence is strong enough to create or link a company.

Company creation is allowed when

A non-placeholder company_name exists and at least one corroborator exists: website, LinkedIn URL, company external ID, phone, or address.

It is intentionally suppressed when

The name is a work-status placeholder such as self-employed, freelance, unemployed, or retired; or the row has only a company name with no corroborating attribute.

Suppression does not discard the employer cells: their observations remain queryable with complete provenance. Qualified evidence is passed through the normal company key/scoring algorithm, then the raw record gains an employer role link and the person/company entities gain an employed_at relationship with source evidence. The source is treated as describing an organisation for this sub-flow even if the original file describes people.

Relationship history: discovering a new employer does not automatically close an older employed_at relationship. The current pipeline accumulates evidence; it does not infer start/end dates or declare that a former job ended.

13 · Phase 6

Golden-record selection: one answer, all evidence

The golden layer does not overwrite source observations. For every entity and canonical field, it chooses a current answer, calculates confidence, keeps alternatives, and records a temporal history whenever the chosen value changes.

Confidence calculation

confidence = clamp(0.05, 0.99, winner source reliability + 0.15 × (supporting sources − 1) − 0.10 × dissenting sources)

Support and dissent are counted by distinct source. Repeated rows from the same feed cannot manufacture consensus. The result is rounded to three decimals. Every losing value is retained in alternatives with its evidence, making it possible to explain both the answer and the confidence score.

Exact no-op

Same answer, support counts, competition counts, and confidence: keep the row untouched.

Refresh in place

Same answer but changed counts/confidence: update the open row while preserving its valid_from.

New historical version

Different answer: close the old row, insert the new current row, and connect supersession metadata.

Golden builds commit per entity. A failure on one entity does not erase completed builds for earlier entities. There is currently no automatic retirement of a source observation; source evidence remains eligible until application logic changes it or an entity merge changes ownership.

14 · Optional human-reviewed phase

AI enrichment: propose first, write only after approval

Enrichment fills a deliberately narrow set of missing classifications. The model never writes directly into an entity’s golden row: it creates a pending proposal, and an operator either accepts or rejects that proposal with a permanent audit trail.

Eligibility and generation

  1. Select an active entity with at least one golden attribute. Its target field must be missing and it must have no prior enrichment attempt for that field.
  2. Process the oldest work first. The default command limit is 25 entities per requested field.
  3. Require context. At least two known golden fields must be available before a model request is made.
  4. Apply a deterministic quality gate. The answer must be non-empty and model confidence must be at least .55.
  5. Persist the outcome. Written proposal, declined response, and model/error failure are all attempts. This prevents hidden infinite retries.

What acceptance really writes

Acceptance creates or reuses a synthetic source named ai_enrichment with low reliability .20, plus a completed synthetic batch. It stores a raw record, normalizes the proposed value, writes a canonical observation, and self-links that record to the already known entity with match confidence 1.0. The proposal becomes accepted. This preserves the same provenance shape as ordinary source data instead of smuggling a value directly into golden_attribute.

Follow-through differs by caller. The core acceptance function does not run validation and does not itself rebuild golden attributes. The review console immediately runs the golden rebuild after a successful acceptance. A direct CLI or library caller must arrange that follow-up explicitly.

15 · Delivery boundary

Serving projection: publish a simpler read model

The pipeline database is optimized for provenance, decisions, and history. The serving database is deliberately simpler: one companies row and one leads row for downstream systems. Projection is a one-way, restartable copy—not a second source of truth.

How output fields are formed

  • Scalar columns come from current golden attributes.
  • Industry, technologies, keywords, SIC, and NAICS arrays are distinct values gathered from observations.
  • Person company_id follows the employed_at relationship.
  • Overall confidence is the mean of available golden-field confidences.
  • The representative source is the source that wins the most projected fields.

Rows that cannot be published

  • Entities without a usable display/name value are skipped.
  • Serving uniqueness or type failures roll back only that row’s savepoint.
  • Every rejected entity and database reason is included in the run report.
  • If any row is rejected, the watermark does not advance, ensuring the next incremental run can try again.

Watermark logic

The watermark lives in the serving database. An incremental run reads entities changed after the prior watermark and captures the pipeline database clock at the beginning of the run. Only a fully accepted run moves the watermark to that captured time; work committed during the run therefore falls into the next window. A full rebuild option ignores the prior watermark.

Projection is currently upsert-only. If a pipeline entity is absorbed, deleted, or loses an output value, the projector does not delete/tombstone the stale serving row or necessarily clear an old field. Consumers that require hard deletion semantics need an explicit reconciliation extension.

Consumer failure classification

Success

Commit database work, publish and flush the next event, then commit the input offset.

Permanent domain error

Log the bad/stale message and commit its offset so one impossible event cannot poison the partition forever.

18 · Cross-cutting storage

Database model: evidence, decisions, and current answers

The schema is easiest to understand as layers. Source facts are immutable evidence; mappings and rules are versioned interpretations; identity links describe who the evidence belongs to; golden attributes are replaceable answers derived from all of it.

The short answer: there are not 26 competing copies of a person or company. Each table remembers one kind of fact at one level of detail. Most readers should begin with golden_person or golden_company; the other objects exist so the system can explain, review, and safely recompute those answers.

Pipeline database · authoritative

Owned by this repository. It contains parsed source rows, current interpretation/review decisions, durable identities, current golden values, queues, operating state, and preserved version/event history where the model provides it. Its schema is the 25 ordered migrations in db/migrations.

Serving database · projection target

Owned by the display application. It receives simple companies and leads rows for fast application reads. It is downstream, intentionally loses most lineage, and must never be used to reconstruct pipeline truth.

Why separate tables instead of one giant row?

Different quantities

One source has many batches; one batch has many records; one record has many cell observations and rule results; one entity can have many records. A single flat table would repeat source and entity data thousands of times.

Facts versus judgements

raw_record preserves the parsed input. Mapping, validation, matching, and golden selection say what the system concluded. Keeping them apart lets conclusions change without rewriting raw evidence; version/event history is retained where the model explicitly provides it.

Current state versus history

record_validation, quarantine_item, and pipeline_control answer “where is it now?” Their result/event companions answer “how did it get here?” Both questions stay fast and auditable.

Stable identity versus changing values

entity is only the durable person/company ID. Names, jobs, employers, and addresses can change, so they live as linked observations, relationships, and temporal golden attributes.

Failures have different meanings

quarantine_item means the row was understood but failed a data rule. record_error means code or storage could not process it. Combining them would blame vendor data for system failures.

Views are saved queries, not copies

A view stores SQL, not another set of people. It filters or joins the tables at read time, giving callers a safer, simpler contract without another dataset to synchronize.

Database permissions are not the workflow guardrail here. Services use the same configured PostgreSQL account, so ownership is primarily enforced by repository code and convention rather than per-table grants. PostgreSQL may accept a hand-written UPDATE that bypasses a required event, merge, temporal close, replay, or reviewer field.

Indexes, constraints, and migrations are not extra datasets

Constraints protect meaning

Primary and foreign keys keep lineage connected; checks restrict states/scores; uniqueness makes retries idempotent—for example one mapping per layout column and one current golden value per entity/field.

Indexes protect speed or uniqueness

Lookup, status, foreign-key, and partial indexes accelerate the paths the services actually use. They are maintained from table data and are not another business record to query.

Migrations are change history

Migration number is not table number. Some migrations create several objects; others only alter a column, replace a view, or add indexes. They run forward once and are checksum-locked.

20 · Runtime, observability, and trust boundary

Operations, deployment, and security

Operational logic is part of data correctness: credentials must resolve predictably, pauses must survive restarts, failures must be observable, and recovery must not silently advance work. This section separates what the software enforces from what deployment must provide.

Configuration and secrets

setting resolution: direct environment value → NAME_FILE path → /run/secrets/name → application default

This precedence supports local .env-style operation and container secret files with the same code. PostgreSQL DSNs percent-encode credentials, default to a 10-second connect timeout, and use a 300,000 ms statement timeout. Kafka bootstrap addresses, filesystem paths, review-console keys, and optional AI endpoint/model/timeouts are also centralized in common settings.

Health, supervision, and persistent controls

Heartbeat database writes are throttled to roughly once every 15 seconds. The supervisor expects the watcher plus all five batch consumers and checks Kafka availability. It owns only its own protective ingestion pause: after three consecutive clean checks it may resume that pause, but it must never override a human-owned or circuit-breaker-owned pause.

Logging, metrics, integrity, and alerts

Structured logs

Services log to stdout. Warning/error records are also queued asynchronously for service_log.

Non-blocking DB log sink

Queue max 2,000; flush around 100 rows or one second; failures drop/cap diagnostics rather than stall pipeline work.

Metrics

PostgreSQL gauges use a 12-second cache against a 15-second scrape. Kafka posture is collected independently.

Integrity

Twelve invariant queries and alert rules expose orphaned evidence, broken current rows, stalled work, and service posture.

If the metrics database query fails, the endpoint publishes an “up = 0” style signal rather than serving stale database gauges as if they were current. Prometheus, Grafana, and Alertmanager configurations are included. The console’s liveness endpoint proves only that the web process responds; readiness additionally runs SELECT 1 against PostgreSQL.

Recommended investigation order

  1. Read the durable state first. Batch, queue, control, quarantine, candidate, and error rows outlive a process restart.
  2. Identify ownership. Human, breaker, and supervisor pauses have intentionally different resume rules.
  3. Check the last committed boundary. A terminal event can be missing even when database work is present; never infer data absence from Kafka alone.
  4. Repair the smallest unit. Replay one record, rerun one batch stage, or rebuild one entity before choosing a global rebuild.
  5. Verify downstream materialization. Decisions often need resolution/golden/projection follow-through.

24 · Developer playbook

How to change the pipeline safely

Most changes cross more than one module. Use these checklists to preserve provenance, versioning, replay safety, human review, and downstream shape while adding capability.

Add or change a canonical field
  1. Add the field specification, aliases, subject, detector, and normalized type in common/canonical.py.
  2. Bump CANONICAL_SCHEMA_VERSION when meaning or vocabulary changes; old layout decisions must remain distinguishable.
  3. Add header/ambiguity/collision/value-detector mapping tests, including employer/self collisions where relevant.
  4. Confirm its normalizer exists and add null, empty, malformed, Unicode, and multi-value tests.
  5. Add appropriate validation rules—or deliberately document why no rule applies.
  6. Decide whether the field can form an identity key; default should be no.
  7. Choose a golden strategy and test source, recency/frequency, support, dissent, and tie behavior.
  8. If consumers need it, add a serving migration and explicit projector mapping; never rely on name coincidence.
  9. Update this canonical table and regenerate/review fixtures.
Add or change a validation rule
  1. Give the rule a stable ID, precise severity, clear human message, and structured evidence.
  2. Register it only for the normalized types/fields where it is meaningful.
  3. Bump RULESET_VERSION if verdict interpretation changes, preserving prior results as historical evidence.
  4. Test pass/fail and every boundary; also test the wrapper’s exception-to-rule.error behavior.
  5. Re-evaluate record status, quarantine transitions, and breaker false positives using representative corpora.
Add an identity key or alter a weight
  1. Define one deterministic canonicalization; equivalent inputs must produce exactly the same key bytes.
  2. Choose strong versus moderate based on collision risk, not availability.
  3. Add the key weight and candidate evidence representation.
  4. Test sorted advisory-lock acquisition, duplicate-key ownership, source scoping, ties, and active/absorbed entities.
  5. Prove moderate combinations cannot cross auto-link unless that policy is intentionally changed.
  6. Run parity/concurrency/corpus measurements before backfilling existing entities.
Add a pipeline stage or event
  1. Define the authoritative database state first; keep event payloads as references.
  2. Specify input/output event schema and permanent versus transient failures.
  3. Make the stage idempotent under redelivery and define its transaction boundary.
  4. Publish output only after commit; commit input offset only after output delivery.
  5. Add heartbeat, service name, structured logging, metrics, supervisor posture, deployment, and alerting.
  6. Add manual recovery behavior and document whether manual execution emits the next event.
Change a database table
  1. Create the next forward-only numbered migration; never rewrite a migration already applied elsewhere.
  2. Make constraints express the invariant whenever PostgreSQL can enforce it.
  3. Plan lock duration and backfill separately for large tables; migration connections intentionally can disable statement timeout.
  4. Update repositories, views, lineage queries, integrity checks, console serializers, fixtures, and serving projection as applicable.
  5. Test upgrade from the prior migration state and perform a restore rehearsal before production rollout.
The best regression test describes the invariant in its name: “a moderate key never auto-links,” “an invalid record is not resolvable,” or “replaying normalization does not duplicate observations.” These survive refactors better than tests coupled only to implementation shape.

27 · Shared language

Glossary

Attribute observation

One normalized interpretation of one source cell/list element, with raw provenance, subject, mapping status, and normalization outcome.

Batch

One ingestion of a file or selected worksheet for one configured source.

Canonical field

The stable target vocabulary—such as email or employee_count—onto which arbitrary source headers are mapped.

Canonical observation

An observation whose column mapping is auto_accepted or human approved; other observations remain captured but do not drive business logic.

Entity

A durable person or company identity to which one or more source records may link.

Golden attribute

The current best value for one entity field, including confidence, support, alternatives, and a validity interval.

Identity key

A normalized lookup value (email, external ID, domain, composite name/city, and so on) used to generate and score entity candidates.

Layout fingerprint

SHA-256 of the ordered original column-name list. Column order matters, allowing mapping decisions to be safely reused only for the same layout.

Mapping confidence

Confidence that a source column means a canonical field. It is not data validity, entity-match confidence, or golden confidence.

Match candidate

An unresolved possible entity merge that needs human acceptance or rejection.

Provenance / lineage

The trace from a golden answer through entity link and observation back to raw row, source column, file, batch, and source.

Quarantine

A durable routing decision that blocks an invalid record from automated resolution while retaining every source value and rule result.

Record error

A processing exception for one record, stored with the original bytes for replay. It is distinct from a data-quality quarantine verdict.

Reliability

A configured trust score for a source, used mainly by golden survivorship. It does not prove an individual value is valid.

Ruleset version

The semantic version identifier stored with validation results so a later rule change does not rewrite what an earlier run concluded.

Subject

Whose fact a cell contains. In a person row, self describes the person and employer describes a company.

Strong / moderate key

Identity-collision classification. Moderate evidence is intentionally unable to reach automatic linking by combination alone.

Watermark

The serving database’s last fully clean projection time; it defines the lower boundary of the next incremental copy.

Current implementation notes and known boundaries

This is the “do not learn the wrong lesson” section. The preceding sections describe the intended model and current happy-path behavior. The items below are observable boundaries or edge cases in commit 021da8c. Some are conscious tradeoffs; others are gaps worth fixing before relying on the stronger behavior in production.

These notes are documentation findings, not evidence of data corruption. They identify the exact situations where an operator or future change must supply an additional guarantee.

Pipeline and event boundaries

PriorityCurrent behaviorOperational implicationRecommended hardening
HighThe control table/UI names mapping, normalization, validation, resolution, golden, and ingestion, but only ingestion and validation paths call a control guard or pause partitions.Pausing one of the other four stages in the console records intent without stopping its consumer.Add the same durable guard/partition-pause contract to every consumer, or limit the UI to controls that are enforced.
HighResolution commits each record before publishing one entities.resolved event. If the final publish fails, redelivery finds no unresolved rows and raises a permanent BatchNotResolvable.The offset can then be committed without a golden trigger even though resolution data is complete.Persist an outbox/stage-completion record, or make a replay reconstruct and republish the affected entity list.
MediumThe mapping consumer writes the outgoing event’s schema_version from the incoming batch event, falling back to "1". The stored canonical vocabulary is v4.Event metadata can say v1 even when the mapping was made under v4; database rows remain authoritative.Publish the version stored with source_schema or the current canonical constant.
MediumThe record path commits each row, queues its terminal event, and flushes the producer only after the file loop. A crash or flush failure can occur after database commits but before every notice is durable.External consumers of record.processed may miss notifications even though authoritative records/entities exist.Use a transactional outbox or a database-driven republisher keyed by the batch’s event-publication marker.
Contractpcdf.raw_record.ingested is defined and provisioned but has no current publisher or consumer.External teams should not infer record-level ingestion notifications from topic existence.Mark it formally reserved/deprecated, or implement and test a complete ownership contract.
MediumManual console stage runs call phase functions directly and intentionally do not publish the next event.A repaired stage does not automatically rejoin the rest of the Kafka chain.Show the required next stage prominently, or add an explicit operator option to emit a completion event after verifying state.

Record path and quality boundaries

PriorityCurrent behaviorOperational implicationRecommended hardening
HighWhen the record-path breaker stops a file, run_file() returns RunResult(stopped=True). The watcher checks only exceptions and then moves the file to _done; its RunStopped handler is not reached.A partially read, failed/inert batch can receive a “done” filesystem receipt.Have process_file() inspect result.stopped and move the file to _failed with recovery instructions.
MediumAfter the record path creates/commits its batch row, some exceptions before or around the main drive can escape without marking that batch failed.A running batch can remain and its in-flight hash blocks retry until an operator abandons it.Wrap post-create work in a finalizer that records failure/stopped state while preserving the original exception.
MediumWith a configured record-ID column, batch ingestion rejects a file that lacks the column; the record path falls back to row number because it calls row.get().The same bad configuration has different outcomes on the two paths.Share one strict source-record-ID helper and parity test.
MediumThe person name_company key expects company_name among self values, but canonical v4 maps it to the employer subject. Person phone keys also consume only generic phone, not the five qualified phone fields.These defined/available signals normally do not improve person candidate recall.Build the composite deliberately from employer evidence and decide which qualified phone fields are safe blocking keys.
PolicyResolution and golden selection read canonical non-null observations but generally do not exclude values with attribute-level validation errors. TradeoffOptional synchronous_commit = off preserves transaction ordering but can lose a recent committed suffix on a database crash.The batch should remain uncompleted/inert, but “commit returned” is not a durability promise in this mode.Use only for reconstructible bulk loads and document/rehearse file-level retry.

Review, golden, and enrichment boundaries

PriorityCurrent behaviorOperational implicationRecommended hardening
MediumA same-value golden row refresh is detected using support list, competing values, and confidence. If the winning record/source/evidence changes while those scalars stay identical, the row is counted unchanged.Lineage metadata can remain pointed at an older winning observation even though the displayed answer is correct.Include winning IDs and evidence in the equality comparison or always refresh same-value metadata.
HighEnrichment acceptance reads a pending proposal without FOR UPDATE, writes synthetic evidence, then conditionally marks the proposal accepted without checking the update result.Two concurrent accepts can both create evidence/batches even though only one status transition wins.Lock the proposal row first, or atomically claim it before writing any evidence.

TradeoffAny AI outcome—proposal, decline, or error—creates an attempt and prevents automatic retry for that entity/field.A transient model outage needs a manual reset/new policy rather than silently retrying forever.Keep this if audit/expense control is primary; otherwise distinguish retryable infrastructure failures from completed attempts.
MediumRepeated pause updates write pipeline_control_event.from_state as the logical inverse of the destination instead of reading the actual previous row.A pause-while-paused audit event can incorrectly claim it came from running.Lock/read the current control row and persist its real state in the event.
TradeoffEmployer changes add employed_at evidence but do not close earlier relationships or infer effective dates.Consumers cannot treat every open relationship as a guaranteed current job.Add source-dated relationship validity rules before exposing “current employer” semantics.

PriorityCurrent behaviorOperational implicationRecommended hardening
HighThe upload worker’s advisory lock covers only the short claim transaction. Two console replicas can claim different items and ingest them concurrently even though comments/UI describe a globally serial queue.Horizontal console scaling reintroduces interleaved ingests and competing resource use.Hold a session-level worker lease for the full ingest or deploy exactly one active queue-worker replica.

Final orientation

If you are debugging data

Walk backward: golden attribute → entity link → observation → raw record → batch → source, then inspect mapping and rule versions.

If you are recovering work

Find the last committed database boundary, preserve its audit state, and replay the smallest idempotent unit.

If you are extending code

Protect five properties together: provenance, versioning, replay safety, concurrency, and human-review semantics.

The single most useful sentence to remember is: raw evidence is permanent; interpretations are versioned; identities are conservative; golden answers are rebuildable.
