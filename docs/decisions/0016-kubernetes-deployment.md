# ADR 0016: Deployment beyond one machine

## Status

Accepted, partially verified. See the "Verification" section below before
treating this as equivalent in confidence to ADRs 0001-0015 — every one of
those was proven against a live stack; this one was proven against
`kubectl kustomize` and `docker build` because no Kubernetes cluster was
reachable while it was built.

## Context

The README has said this since ADR 0015: "Docker Compose is the only
deployment. Single Postgres, single Kafka broker, no orchestration and no
staging environment. Fine for one machine; not fine for an uptime
commitment." Every other README caveat in that same list — credentials only
as environment variables, alerts with nowhere to go, files loaded by hand —
got closed in increment 15. This one had not.

The two things Compose's single-host assumption is load-bearing for:

- **Two bind mounts.** `./data` and (read-only) `./tools` are on the host
  Compose is running on. Every service can reach them because there is
  exactly one host. Once a pod can be scheduled onto any node in a cluster,
  a bind mount to "the host this happens to be running on" stops meaning
  anything.
- **One broker, one Postgres.** Compose's `kafka` and `postgres` services are
  each a single container. A single Kafka broker is a single point of
  failure regardless of how many machines the *cluster* has; deploying to
  Kubernetes without also fixing this would move the orchestration problem
  and leave the durability problem exactly where it was.

## Decision

**Kubernetes manifests under `infra/k8s/base/`, built with kustomize.**
Not Helm: every other configuration surface in this repository is plain YAML
or a `.env` file, none of it templated through a second language, and a
chart would be the first templating layer in the project. kustomize's
`configMapGenerator` reads the *same* `infra/prometheus/`,
`infra/alertmanager/` and `infra/grafana/` files Compose already
bind-mounts, so Prometheus's rules and Grafana's dashboards have one copy on
disk under either deployment method.

**`tools/` moves from bind-mounted to baked-in**, in
`services/record_pipeline/Dockerfile` only — the one image that already
carries every stage package `reblock.py`, `rebuild_golden.py` and
`purge_source.py` need. `docker compose run --rm pipeline python
/tools/ops/reblock.py` and its neighbours keep working unmodified, because
the path inside the image is still `/tools`; a cluster operator runs the
same script with `kubectl exec` instead.

**Kafka goes from one broker to three**, KRaft mode, on a StatefulSet. Each
pod derives its own `KAFKA_NODE_ID` and `KAFKA_ADVERTISED_LISTENERS` from
its ordinal at container start — a documented approach for running Kafka's
combined broker+controller mode without a second image or a Helm values
file, though (see Verification) not one watched form a quorum here.
`libs/common/src/common/kafka.py`'s topic replication factor, previously a
hardcoded `1`, is now `settings.kafka_topic_replication_factor` — a `1`
against three brokers would mean a topic's only copy sits on whichever
broker happened to create it, which defeats the point of the other two.

**Postgres stays a single instance.** A second pod with its own
`PersistentVolumeClaim` is a second, empty database, not a standby; real
failover needs streaming replication (Patroni, CloudNativePG) and is not
what this increment builds. What Kubernetes *does* buy Postgres here without
that — a stable volume and a stable name across a reschedule, versus
Compose's "whichever host happens to have `postgres-data`" — is real and is
taken.

**Secrets reuse ADR 0015's seam exactly.** `common.config.resolve()` already
reads `/run/secrets/<name>` without being told to, because that is where
both Compose secrets and Kubernetes secret volumes mount one. The
`pcdf-secrets` Secret's keys are lowercase and match the same filenames
`docker-compose.secrets.yml` already produces, mounted at the same path.
Zero application code changed for the "real secret store" gap either — the
seam already generalized past Compose, which is what it was built to do.

**Rejected: a Helm chart.** Considered so the image tag and replica counts
could be template values instead of a `sed` over `infra/kustomization.yaml`.
Rejected because it would be the first place in the repository where
configuration is generated by a templating language rather than read
directly, and the actual variation between environments here — a registry
host and a handful of replica counts — does not need one.

**Rejected: a CronJob backup/restore for Kubernetes in this pass.**
`tools/ops/backup.sh` and `restore_check.sh` are Compose-shaped
(`docker compose exec`); a `pg_dump` CronJob against the `postgres` Service
is the right equivalent but was not built here, to keep this increment to
what could actually be checked (see Verification) rather than adding a
second unverified surface. `infra/k8s/README.md` documents the manual
`kubectl exec pg_dump` in its place and names this as the gap.

## Consequences

- Deploying now means building and pushing eight images to a registry
  first, where Compose only ever needed a local build. `infra/k8s/README.md`
  spells out the loop.
- Kafka's replication factor is now a setting instead of a constant, so a
  Compose user's single broker and a Kubernetes user's three brokers can
  each be correct without either editing library code — but it does mean
  `KAFKA_TOPIC_REPLICATION_FACTOR` unset now silently defaults to `1`
  everywhere, including a Kubernetes deployment that forgot to set it in its
  ConfigMap. `infra/k8s/base/01-configmap.yaml` sets it to `3` and says why.
- `services/record_pipeline`'s image is larger (`tools/` baked in). Nothing
  else changed about it: same base layers, same non-root user, same
  read-only everything-except-`/data` posture ADR 0001's Dockerfiles
  established.
- Of the three "Future increments" bullets this README carried since ADR
  0015, only deployment is addressed here, and only partially: it moves from
  "future" to "written, partially verified" — not to "done" in the sense
  every prior increment's ADR could claim it. A real secret store (Vault or
  a cloud KMS behind the same seam) and scheduled collection (an SFTP poll
  or vendor API client feeding the watcher) are both still open; this
  increment reused the existing file-based seam for the new deployment
  target rather than replacing what sits behind it.

## Verification

Run without a cluster, because none was available:

- `kubectl kustomize infra` renders successfully — 7 ConfigMaps (1 static,
  6 generated), 10 Deployments, 2 StatefulSets, 1 Job, 4
  PersistentVolumeClaims, 7 Services — and every generated ConfigMap's
  hash-suffixed name appears exactly twice in the output: once as the
  object, once as the volume reference kustomize rewrote automatically.
- `services/record_pipeline/Dockerfile` with `tools/` baked in builds
  clean; inside the built image, `/app/tools/ops/reblock.py` is owned by
  the non-root `app` user and `python /app/tools/ops/reblock.py --help`
  prints its full usage text.
- `uv run pytest` across `libs/common` and the five stage services — 380
  tests — passes with `kafka_topic_replication_factor` in place of the old
  constant.
- `process watch --help`, `python -m common.migrations` and
  `mapping-consumer`, run standalone against the images `docker compose
  build` already produces, each reach their Postgres/Kafka connection
  attempt with no argument-parsing or import error.

Not run, because there was nothing to run it against — see
`infra/k8s/README.md`'s "What was not checked" section in full: whether the
three Kafka pods actually form a KRaft quorum, whether a real cluster's
default StorageClass binds these PVCs, and everything downstream of a
successful `kubectl apply` this pass never got to attempt.
