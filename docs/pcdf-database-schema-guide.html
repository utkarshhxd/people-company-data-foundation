A tour of the pgAdmin schema, in plain words

The Golden Record Schema

25 tables and 8 views sound like a lot until you notice they're one idea, repeated: never overwrite what a source said, only add a judgement on top of it. Every table below is either recording a fact, judging a fact, or deciding which fact wins.

25 tables 8 views 2 databases — pipeline (this guide) & serving (the app) 1 rule — nothing a vendor said is ever deleted

Think of the pipeline database as a court case, not a spreadsheet. A vendor file is a witness giving testimony (an observation). Several witnesses can disagree. A judge — the golden stage — picks the value to trust, but the losing testimony stays in the transcript forever. That's the whole schema: tables that hold testimony, tables that judge it, and one table that records the verdict.

Reading it in pgAdmin: everything above lives under one schema, public, in the pcdf database. Solid boxes in the diagram are real tables; a few things you'll see in the tree — golden_person, golden_company, person, company, resolvable_record — are views: saved queries that look like tables but store nothing of their own. pgAdmin marks them with a different icon; this guide marks them with a dashed border and a "view" badge.

Five things that sound alike but aren't

The single most confusing thing about this schema is that it stores five different kinds of "how sure are we?" — and every migration comment goes out of its way to say they must never be mixed up. Once you can tell these apart, every table below makes sense.

A

Source reliability

source.reliability — how much do we trust this vendor in general?

B

Mapping confidence

column_mapping — how sure are we this column means "email"?

C

Validation outcome

validation_result — is this one value well-formed and usable?

D

Match confidence

record_entity_link — is this row the same person as that one?

E

Golden confidence

golden_attribute — how sure are we in the chosen value overall?

A perfectly-mapped column (B) from a trusted vendor (A) can still hold a broken email (C fails). A record can pass every validation rule and still be a weak match to the entity it landed on (D). None of the five can substitute for another — that's why each gets its own column, in its own table.
01

Ingestion — what a source literally handed us

Before any judgement happens, the file's contents have to exist in the database exactly as the vendor wrote them. These four tables never interpret anything.

sourcetable

One row per vendor or feed — not per file. "Apollo," "c_suite," and "LeadsNemo" each get exactly one row here, no matter how many files they've sent.

source_typecsv, excel, or (later) ai_enrichment for the AI's own guesses.
reliability0–1, dimension A above. Set by a human, once, per vendor.
describesorganisation or location — does a shared domain mean one company, or one street address? (Two Subway franchises share subway.com and are not the same business.)
batchtable

One row per upload — the file you actually dropped in the folder or ran through the CLI.

statusrunning, completed, failed.
rows_read / rows_ingested / rows_skippedthe file's scoreboard.
file_hashfingerprint of the bytes — how a re-dropped file is recognized as "already loaded."
columnsthe column names, in the exact order the file had them (jsonb can't be trusted to keep order on its own).
events_published_atNULL means the rows are safely in Postgres but the "batch is ready" announcement never made it to Kafka — a visible gap instead of a silent one.
raw_recordtable

One row per source row, kept verbatim as JSON. This is the row your vendor sent — untouched, forever. Every other table in the database ultimately points back to a row here.

raw_payloadthe entire row as jsonb — every column, unmapped ones included.
source_record_ida natural key if the file had one, otherwise just the row number.
record_errortable

Where a row goes when the pipeline couldn't even process it — a malformed cell, a crash, a bug. Not a judgement about the data (that's quarantine, stage 05); this is a confession that our own code choked.

raw_payloadstored here too, because the failure may have happened before raw_record was even written — this table can be the only proof the row ever arrived.
stagefree text, not a fixed list — new stages get added, and a strict CHECK here could reject the very error it's meant to record.
Every table from here on repeats the same three columns: batch_id, source_id, and usually record_id. They're the provenance trail — the answer to "which file, which vendor, which row" is always one join away, on every table in this schema. This guide won't repeat that for every card.
02

Schema mapping — naming the columns

A vendor's column is called "Work Email" or "email1" or "E-Mail Address." Something has to decide that all three mean the canonical field email — and remember that decision so a human never has to make it twice for the same layout.

source_schematable

One row per distinct column layout a source has ever sent — not per batch. If Apollo sends the same 40 columns in the same order every week, that's one row here reused every time.

column_fingerprinta hash of the ordered column list — "this exact layout," so a repeat is recognized instantly.
column_mappingtable

One row per source column, saying which canonical field it is — or that nothing matched.

canonical_fieldNULL is allowed and means "unmapped," not "ignored" — the raw column still gets captured in stage 03.
mapping_methodexact_alias, similarity, value_analysis, ai_suggestion, manual, corroborated, or none — how the guess was made.
mapping_confidencedimension B from above.
mapping_statusauto_accepted, needs_review, unmapped, approved, rejected — needs_review is what shows up in the review console.
subjectself or employer — "Company City" on a person row describes the employer, not the person. Getting this wrong would make a person's golden address collide with their employer's.
03

Normalization — the lossless layer

This is the one table that matters most for the promise "nothing a source said is ever lost." Every single cell of every single row — mapped or not — becomes its own row here.

attribute_observationtable

One row per cell. A 40-column file with 10,000 rows produces up to 400,000 rows here. This table is append-only — a later observation never overwrites an earlier one; deciding which one "wins" is the golden stage's job, not this table's.

raw_value / normalized_valueexactly what the source wrote, and the cleaned-up comparable form. normalized_value is NULL when the source wrote a placeholder like "N/A" — the raw text is kept, but downstream code won't mistake the placeholder for real data.
value_indexone cell can contain several values (vendors really do use a ^^ delimiter) — each becomes its own observation instead of one squashed string.
subjectself or employer, inherited from the column's mapping.

An unmapped column (FAX_NUMBER, SIC_DESCRIPTION, profile_pic…) still lands here with canonical_field = NULL. It's captured, just not yet promoted to a "real" field.

04

Validation — is this value usable?

Validation never fixes anything and never deletes anything. It only attaches a judgement next to the untouched observation.

validation_resulttable

One row per rule run against one value (or against the whole record, for record-level rules). Passes are stored, not just failures — otherwise there'd be no way to tell "the rule passed" from "the rule never ran."

scopeattribute (one value) or record (the row as a whole).
severity / outcomeerror, warning, or info; pass or fail.
ruleset_versiona judgement is only meaningful against the rules that made it — a new ruleset writes new rows rather than rewriting history.
record_validationtable

One row per record — where it stands right now. If validation_result is the trial transcript, this is the verdict.

statusvalid, warning, or invalid. Invalid means "not safe to resolve yet," never "delete this."
validated_attributes / unvalidated_attributesmakes coverage countable — a record that's 90% unvalidated (mostly unmapped columns) is not the same as one that passed everything.
05

Quarantine — held, never dropped

An "invalid" record has to go somewhere that isn't the trash and isn't the entity graph. Quarantine is that somewhere, and it's written in the same transaction as the invalid verdict — no gap where a bad record is loose.

quarantine_itemtable

One standing row per quarantined record — its current state.

reason_codeswhich rules put it here, so a reopen can tell "same problem" from "new problem."
quarantine_eventtable

Append-only history of every disposition change — who did what, and when. quarantine_item is "now," this table is "the whole story."

resolvable_recordview

Not a table — the actual gate. Entity resolution reads this, never raw_record directly. A record is resolvable if it's valid/warning and not rejected, or if a human explicitly released it.

06

Entity resolution — whose fact is this?

Everything before this stored what sources said. Here, records become observations of something — a stable person or company that survives the vendor changing, the name changing, even records merging.

entitytable

The real-world person or company. Deliberately holds no attributes — which name is "the" name is the golden stage's decision, not this table's. An entity is just an identity.

status / merged_into_entity_ida merged entity is never deleted — it becomes a tombstone pointing at the survivor, so any id ever handed out still resolves.
person = a view over entity WHERE entity_type='person' company = a view over entity WHERE entity_type='company'
record_entity_linktable

Which entity a source row is about. This is the join between "what was said" and "who it was said about."

roleself or employer — one person row can link to two entities: itself, and the company it names as employer.
match_statusauto_linked, new_entity ("nothing matched, so start fresh" — recorded as deliberately as a match), or manual.
match_confidencedimension D.
entity_identity_keytable

The values that make an entity findable — an email, a domain, a phone. Candidate matching reads only this table, so it never has to scan every entity in the database.

strengthstrong keys can carry a match on their own; moderate ones never can alone — this is what stops two different people at the same company from merging on company name alone.
match_candidatetable

A match that scored high enough to be worth a human's attention, but not high enough to act on automatically. The record still gets its own entity in the meantime — the pipeline never blocks waiting on a review.

entity_mergetable

Append-only proof of every merge — what got absorbed, into what, by whom, why. Merging is the one operation here that looks irreversible, so it gets the most permanent record.

entity_relationshiptable

Relationships between entities. Today only one kind exists: employed_at.

entity_observationview

The answer to "what do we know about this person, and who told us." Joins record_entity_link → attribute_observation → source → batch into one readable row.

07

Golden record — the trusted value

This is the destination. Entities hold no attributes of their own (stage 06) — this is where "which of the three reported names is the name" finally gets decided, and where the decision is made auditable rather than just asserted.

golden_attributetable

One row per value a field has ever held for one entity — current and historical together, in the same table, so the two can never drift apart. valid_to IS NULL means "this is the value right now."

strategywhich survivorship rule decided this — so a surprising value always traces back to a policy, never a mystery.
confidencedimension E — confidence in the chosen value, computed from (but distinct from) match confidence.
supporting_sources / competing_valuestwo vendors agreeing is a different claim from one vendor speaking unopposed — and both differ from an actual conflict.
evidenceevery value that lost, and who said it. Losing an argument doesn't erase your testimony.

A unique index enforces exactly one current row per (entity, field) — everything else with a valid_to is history, not a duplicate.

golden_recordview

golden_attribute filtered to just the current rows (valid_to IS NULL).

golden_personview

One flat row per person — name, email, job title, and the employer's name/website reached through the employed_at relationship (not the person's own attributes).

golden_companyview

One flat row per company — identity, firmographics, and the commercial profile (technologies, funding, SIC description).

golden_historyview

Every value a field has ever held, newest first — "what did we believe last month, and what changed it."

08

AI assistance — propose, never assert

The one hard rule governing this section: a model's guess can never become a golden value without a human confirming it. These two tables exist specifically to enforce that pause.

enrichment_attempttable

One row per (entity, field) the model has ever been asked about — whatever the answer was. This is what makes running the job daily cheap: once asked, never asked again automatically.

enrichment_proposaltable

A confident answer, sitting in its own review queue — pending until a human accepts or rejects it. Only on acceptance does it become a real observation, through the exact same path a vendor's file would use.

09

Operations — the pipeline's nervous system

None of these four tables describe a person or a company. They describe the machinery — is it running, should it keep running, and what did it just say.

service_heartbeattable

One row per long-running service, overwritten every sweep. Answers "is it alive right now" for a console that can't see inside eleven separate containers.

pipeline_controltable

Can a stage be paused? Yes — deliberately, per stage. If a vendor changes their export format and every record starts failing validation, this is what stops it at record 500 instead of quarantining ten million records overnight.

pipeline_control_eventtable

History of every pause/resume — who, why, and what the stage was seeing when it stopped itself.

ingest_queuetable

Files waiting to be loaded, as a row instead of a thread in memory. Makes uploads survive a restart and stops ten simultaneous uploads from becoming ten interleaved ingests.

service_logtable

WARNING-and-above log lines from every service, readable in a browser instead of eleven separate docker compose logs calls. A convenience, never a dependency — container stdout stays the complete record.

The serving database — a different building entirely

Everything above answers "what do we know, and how sure are we." The application that customers actually browse needs a different question answered fast: "VPs of Engineering in Berlin at companies over 500 people, sorted by confidence" — one indexed scan, not a five-table join. So there are two databases, and a one-way road between them.

This repository doesn't own the app's schema — leads, companies, users, subscriptions already existed. What this repo adds is a contract that makes the projection possible:

companies.entity_id / leads.entity_idcolumns added

A stable pointer back to the pipeline's entity_id, so re-running the projection updates a row instead of piling up near-duplicates. NULL means "this row predates the pipeline and isn't projected onto."

projection_watermarktable

One row per entity type: how far the last run got. Lives in the serving database on purpose — restore serving from an old backup, and the watermark comes back with it, so the next run correctly re-projects whatever the backup was missing.

user_credit_balanceview

Compares the cached users.credit_balance column against the real ledger total in user_credit_batches — the two can drift, and this view is how you'd catch it.

Array fields don't come from golden_attribute. Things like industry or technologies are lists — a golden value is one value by definition, so a list column would be lying about what survivorship produced. Those are built straight from every distinct value any source ever reported.

Glossary

entity
A real person or company, as a stable id — deliberately holding no data of its own.
observation
One fact, as one source stated it. The atomic, never-deleted unit of this database.
golden value / golden record
The one observation, per entity per field, currently trusted over its competitors.
survivorship
The rule that decides which competing observation becomes golden (recorded as golden_attribute.strategy).
provenance
The unbroken trail from a displayed value back to the exact source cell it came from — batch → source → raw_record → observation.
subject (self / employer)
Whose fact a column or observation describes, when one row names two entities (a person and their employer).
watermark
How far a background job (mainly the serving projection) got last time, so the next run only looks at what changed.
quarantine
Held back from entity resolution pending a human decision — still fully present in raw_record and attribute_observation.
