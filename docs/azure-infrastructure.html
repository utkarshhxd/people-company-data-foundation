01

The whole thing, one page

If you read nothing else.

There is one application — PCDF, a data pipeline that ingests vendor files, resolves them into entities, and serves a golden record through a review console. It needs a database, a message broker, monitoring, and about eight of its own processes.

None of that is bought from Azure. Azure sells this project exactly three categories of thing: virtual machines, a virtual network to put them on, and a blob container to keep a state file in. Everything else — Kubernetes itself, Postgres, Kafka, Prometheus, Grafana, shared storage — runs as containers on those VMs.

The five sentences

  1. Terraform bootstrap creates one storage account, once, to hold Terraform's own state file so it does not live on a laptop.
  2. Terraform main creates a resource group, a virtual network, one subnet, one firewall, three public IPs, three network cards and three Ubuntu VMs.
  3. cloud-init on each VM runs a shell script that installs k3s — the master becomes the control plane, the two workers join it using a generated shared token.
  4. Eight images are built from the same Dockerfiles Compose uses and pushed to ghcr.io; the cluster pulls them with a pull secret.
  5. kustomize applies the whole stack into the pcdf namespace; a Job runs the migrations, then fourteen workloads settle.
02

The rule that decided everything

One sentence from ADR 0021 explains nine tenths of the choices below.

The line

"Everything runs as pods. The cloud supplies a cluster and a registry, and nothing else."

— ADR 0021. Later tightened by ADR 0023 to: the cloud supplies virtual machines, and nothing else.

Why

Azure sells a managed Postgres with point-in-time restore, a managed Kafka endpoint (Event Hubs), and a managed Grafana. Each one deletes a StatefulSet and some operational work. Taken together they also turn "can we run this somewhere else" from a redeploy into a rewrite.

This system's entire premise is that data outlives the thing displaying it. A pipeline that cannot be moved is a strange thing to build under that premise. So the trade was made deliberately and in the other direction: accept the operational burden, keep the portability.

Layer 0 — the account and the region

Before any resource exists there is a subscription, a tenant, and a decision about where on the planet to put things.

Plain

Azure's hierarchy, outermost first: a tenant is the identity directory (who can log in). A subscription is the billing boundary (who pays). A resource group is a folder inside a subscription — every resource lives in exactly one, and deleting the group deletes everything in it. A region is a physical datacentre location; every resource is pinned to one.

The region choice is not cosmetic

Why

An Azure free-trial subscription caps you at 4 vCPUs per region. That single number dictated the shape of the entire cluster.

southindia only offers the newer B-series v2 sizes, whose smallest option is 2 vCPU. Three nodes × 2 vCPU = 6, which blows the cap — so on southindia the 1-master/2-worker shape is simply impossible on trial credit.

indiasouthcentral still carries the legacy B-series family (B1s, B1ms, B2s, B2ms) unrestricted. That allows B2s (2 vCPU) + B1ms (1) + B1ms (1) = exactly 4. The real three-node architecture, fitting the cap precisely.

This is the difference between "we couldn't test the real shape, so we tested a single node" and "we tested the real shape." It was worth moving region for.

Why the state storage sits in a different region

The bootstrap module (§04) defaults to southindia and was applied before the cluster region moved. It was never moved because it does not matter: the state blob is read once at the start of a Terraform run and written once at the end. Cross-region latency on two HTTP requests is noise, and there is no runtime dependency between the cluster and its state file at all.

The resource group that nobody created

NetworkWatcherRG holds three NetworkWatcher_* resources — one each for centralindia, southindia and indiasouthcentral. Nobody ran a command to create them. Azure creates a Network Watcher automatically, per region, the first time a virtual network appears in that region on the subscription. They are free at this scale and safe to leave alone.

The three regions are a fossil record of where VNets have existed on this subscription: southindia (the original AKS cluster), centralindia (an earlier, since-deleted attempt or the subscription default), and indiasouthcentral (today's cluster).

04

Layer 1 — Terraform's own state

deploy/azure/terraform/bootstrap/ · run once per environment, then never again.

Plain

Terraform keeps a state file — a JSON record mapping "the resource I declared in code" to "the actual thing that exists in Azure, with this ID." Without it, Terraform cannot tell the difference between "create a VM" and "the VM I already made is fine, leave it." The state file is Terraform's memory.

By default that file sits next to your .tf files on disk. That is fine until a second person runs Terraform, or your laptop dies.

Why a separate bootstrap module exists

A chicken-and-egg problem: Terraform cannot create the storage account it is about to use as its own backend, because to use a backend it must already exist. So one tiny module creates it, keeps its own state locally (gitignored), and is never touched again.

This one step stays imperative by necessity. Everything after it is declarative.

What it creates — three resources

ResourceNameDetail
azurerm_resource_grouppcdf-tfstatesouthindia
azurerm_storage_accountpcdftfstated1060b0fStorageV2, Standard_LRS, HTTPS-only, blob versioning enabled
azurerm_storage_containertfstateaccess type private
random_idsuffix4 bytes → d1060b0f, appended to the account name

Why the random suffix

Storage account names are globally unique across all of Azure and may contain only lowercase letters and digits — no hyphens, no underscores. A fixed name like pcdftfstate would collide with whoever bootstraps a second environment, anywhere in the world. Four random bytes solve it: pcdftfstate + d1060b0f.

Why blob versioning is on

State can contain secrets, and a corrupted apply that writes bad state is otherwise unrecoverable — you would be left reconciling reality against a broken file by hand. With versioning, every write keeps the previous blob, so a bad state is one restore away rather than gone.

Run — once per environment 
terraform -chdir=deploy/azure/terraform/bootstrap init
terraform -chdir=deploy/azure/terraform/bootstrap apply

# prints the exact backend-config flags the main module needs
terraform -chdir=deploy/azure/terraform/bootstrap output backend_config_hint

How the main module is wired to it

versions.tf declares an intentionally empty backend block:

terraform {
  required_version = ">= 1.5"
  backend "azurerm" {}   # partial on purpose
}

Account and container names are per-environment and per-subscription, so hardcoding them in a committed file would be wrong. They are supplied at init time instead:

terraform -chdir=deploy/azure/terraform init \
  -backend-config="resource_group_name=pcdf-tfstate" \
  -backend-config="storage_account_name=pcdftfstated1060b0f" \
  -backend-config="container_name=tfstate" \
  -backend-config="key=pcdf-cluster.tfstate"

The live backend, read from .terraform/terraform.tfstate, confirms exactly that wiring, with state blob key pcdf-cluster.tfstate and Terraform 1.15.8.

Interview note

"Where does your Terraform state live, and what happens if two people apply at once?" — Remote, in Azure Blob Storage, versioned. The azurerm backend takes a blob lease as a lock for the duration of an apply, so a concurrent run fails fast with a lock error rather than racing. That is the actual reason to use a remote backend, not just durability.

⚠ Security — the single most important line in this document

admin_cidr defaults to 0.0.0.0/0, and the live NSG confirms it was applied that way. Right now, port 22 (SSH) and port 6443 (the Kubernetes API) on all three VMs accept connections from any address on the internet.

SSH is key-only (Azure's admin_ssh_key block disables password auth), and the k3s API requires a client certificate, so neither is trivially breakable. But both are exposed to untargeted internet-wide scanning, and 6443 in particular is a known scan target.

The fix is one flag on the next apply:

terraform -chdir=deploy/azure/terraform apply \
  -var="ssh_public_key=$(cat ./pcdf-cluster-key.pub)" \
  -var="admin_cidr=$(curl -s ifconfig.me)/32"

That narrows both rules to your current public IP. It has to be re-run when your IP changes, which is the honest cost of not standing up a bastion or a VPN.

Creation order — what depends on what

  1. azurerm_resource_group.main → pcdf

    The folder. Everything else names it. Deleting this group deletes the entire cluster in one call — which is exactly what terraform destroy effectively arranges.

  2. azurerm_virtual_network.main → pcdf-vnet, 10.0.0.0/16
    Plain

    A VNet is a private network inside Azure. Machines on it can reach each other by private IP; nothing outside reaches in unless you explicitly attach a public IP or a gateway. 10.0.0.0/16 reserves 65,536 addresses — vastly more than needed, but address space inside a VNet is free and running out later is painful.

  3. azurerm_subnet.nodes → 10.0.1.0/24

    One subnet, 256 addresses, holding every node. The live private IPs land inside it: master 10.0.1.6, worker-0 10.0.1.5, worker-1 10.0.1.4. (Azure reserves the first four addresses of every subnet, so allocation starts at .4.)

    Why one subnet

    Subnets are a boundary for routing and security rules. Splitting control plane and workers into separate subnets would let you write different firewall rules per role — but here every node runs the same k3s daemon and talks to every other node on the same ports, so a split would buy two subnets and zero isolation.

  4. azurerm_network_security_group.nodes → pcdf-nodes-nsg
    Plain

    An NSG is a stateful firewall. Rules are evaluated by priority, lowest number first, and the first match wins. Azure appends invisible default rules at priority 65000+ which allow all traffic within the VNet and deny everything else inbound — so anything not explicitly allowed below is blocked.

    PrioNamePortSourceWhy it exists
    100ssh22/TCP0.0.0.0/0 openOperator access. Key-only.
    110k3s-api6443/TCP0.0.0.0/0 openkubectl from your laptop. This is what the kubeconfig points at.
    120http-https80, 443/TCP*For an ingress controller that is not installed — opened ahead of time so applying the Ingress later needs no network change.
    130node-to-nodeall, any protocol10.0.1.0/24 internalkubelet (10250), flannel VXLAN (8472/udp), NFS (2049/111/20048), the NodePort range. Restricted to the subnet, never the internet.

    Why rule 130 is a blanket allow rather than an enumerated list: Kubernetes' internal port surface is large, version-dependent and grows (add an ingress controller, a CNI plugin, a service mesh, and the list changes). Enumerating it produces a rule set that breaks silently on the next component. Scoping the blanket rule to the subnet's own CIDR gives the same practical isolation — nothing outside 10.0.1.0/24 matches it — with none of the brittleness.

  5. azurerm_subnet_network_security_group_association.nodes

    Binds the NSG to the subnet. Attaching at the subnet level rather than per-NIC means a new node is covered by the firewall the moment it is created, with nothing extra to remember.

  6. random_password.k3s_token — 32 characters, no specials

    The shared secret that lets an agent node prove it may join the cluster. Generated rather than declared as a variable, so nobody has to invent one or store one.

    Why it never crosses the network in the clear

    It is rendered into the two cloud-init scripts and delivered through Azure's VM provisioning channel — not fetched by the VM over the network at boot. It does, however, end up in the Terraform state file, which is exactly why that file lives in a private, versioned blob container and not in git (§04). special = false avoids shell-quoting hazards when the value is interpolated into a sh script.

  7. azurerm_public_ip.master + .worker[0..1] — Standard SKU, Static
    NameAddressSKUAllocation
    pcdf-master-ip172.198.58.10StandardStatic
    pcdf-worker-0-ip172.198.57.183StandardStatic
    pcdf-worker-1-ip172.198.58.36StandardStatic

    Static, not Dynamic: a dynamic IP is released when the VM is deallocated and a different one is assigned on restart. The master's address is baked into the kubeconfig and into the k3s server certificate's SAN list — if it changed on every stop/start, both would break every time. Static costs a little more and removes an entire class of "it worked yesterday."

    Why the workers have public IPs at all: they do not need one to join the cluster (they join over the master's private IP). They exist for direct SSH to a worker when diagnosing a node-level problem — a `containerd` failure, a full disk — where going through the master is an extra hop. It is a convenience with a cost: three billable addresses instead of one, and two more machines answering on port 22. Setting worker_count aside, dropping worker public IPs entirely and using the master as a jump host would be a strictly tighter design.

  8. azurerm_network_interface.master + .worker[0..1]

    A NIC is the object that actually joins a VM to a subnet. Each one has a single ip_configuration named internal: a dynamic private IP from the subnet, plus the matching static public IP attached. The VM resource references the NIC, not the subnet directly — this indirection is what lets Azure detach and reattach network identity independently of the machine.

    Why version = "latest" is a deliberate risk

    Pinning an exact image version makes builds reproducible but leaves you on an unpatched image until someone bumps it. latest means a rebuilt node gets current security patches automatically, at the price of two nodes built months apart not being byte-identical. For a cluster where nodes are cattle and the state lives in volumes, the patch freshness is worth more than the reproducibility.

  10. azurerm_linux_virtual_machine.worker[0..1] → pcdf-worker-0, pcdf-worker-1

    Identical, except: Standard_B1ms (1 vCPU / 2 GiB), rendered with install-agent.sh.tpl, and — the important line —

    depends_on = [azurerm_linux_virtual_machine.master]

    Terraform would otherwise create all three VMs in parallel, and an agent booting before the server exists finds nothing at https://10.0.1.6:6443 and fails to join. This forces the ordering. It is not a complete fix — the master VM being created is not the same as k3s being ready on it — but k3s agents retry their join indefinitely, so a few seconds of "connection refused" in the agent's log resolves itself.

    The agent template is rendered with azurerm_network_interface.master.private_ip_address, not the public one. Node-to-node traffic stays inside the VNet rather than leaving Azure's network and coming back — faster, free, and not exposed.

Layer 3 — k3s, line by line

infra/k3s/install-server.sh.tpl and install-agent.sh.tpl · under infra/, not deploy/azure/, on purpose.

Plain

k3s is a full, certified Kubernetes distribution packaged as a single ~70 MB binary. It bundles the API server, scheduler, controller manager, kubelet and containerd into one process, and defaults to an embedded SQLite/etcd datastore. It is real Kubernetes — kubectl cannot tell the difference — just assembled for machines that do not have 16 GiB to spare on a control plane.

cloud-init is the standard Linux mechanism for running a script on a VM's first boot. Azure's custom_data field is how you hand a script to it.

Why these files live under infra/ and not deploy/azure/

Neither script names a cloud. Their only inputs are a join token and an IP address. A second cloud's Terraform module — GCP, AWS, a rack — reuses them unchanged; only the module that renders them differs. Putting them under deploy/azure/ would have implied a coupling that does not exist.

The server script, statement by statement

#!/bin/sh
set -eu

-e exit on any failure, -u error on an unset variable. In a cloud-init script that nobody watches run, the alternative is a half-installed node that looks fine until a pod lands on it.

export DEBIAN_FRONTEND=noninteractive
apt-get update -qq
apt-get install -y -qq nfs-common
Why the NFS client is installed before Kubernetes

The cluster runs its own NFS server pod for the shared /data volume (§10), and k3s does not taint the server node — any pod, including one needing that mount, can be scheduled onto the master. NFS mounts are performed by kubelet on the host, not inside the container, so the host needs mount.nfs.

Without this package the failure is: bad option; ... you might need a /sbin/mount.<type> helper program, and the pod sits in ContainerCreating forever. That message does not say "install nfs-common," which is why the comment in the file does.

DEBIAN_FRONTEND=noninteractive stops apt from opening a dialog on a machine with no terminal attached — a classic cloud-init hang.

⚠ The kubeconfig is a root credential

deploy/azure/terraform/kubeconfig holds a client certificate for system:masters — full admin on the cluster, no expiry check beyond the cert's own one-year validity. Anyone with that file plus network reach to port 6443 (which, per §05, is currently the whole internet) owns the cluster.

It is gitignored. Confirm before every commit; treat it like an SSH private key.

Layer 5 — kustomize: base and overlays

infra/kustomization.yaml (base) → deploy/azure/ → deploy/azure-trial/

Plain

kustomize (built into kubectl as -k) layers changes onto a set of YAML files without templating them. A base holds the real manifests; an overlay points at the base and declares the differences. No placeholders, no {{ }}, no second language — the base is valid Kubernetes YAML you can read on its own.

The base: infra/kustomization.yaml

Lists 16 manifest files, generates 6 ConfigMaps from the monitoring config, and declares 8 image placeholders (pcdf-watcher:local → REGISTRY/pcdf-watcher:latest).

Two files are deliberately excluded from resources:

  • 02-secret.example.yaml — a template with CHANGE-ME values. Applying it would create a Secret whose password is literally CHANGE-ME.
  • 31-review-console-ingress.yaml — applying it puts personal data on a public IP. The console shows names, emails, phone numbers, raw quarantined rows and which vendor sold them. It needs a hostname, a certificate issuer and real API keys first. Read its header, then apply by hand.

04-registry-secret.example.yaml is excluded for the same reason as the first — three exclusions, two reasons.

Why the ConfigMaps are generated rather than committed

kustomize appends a content hash to each generated ConfigMap's name and rewrites every reference to it. Editing a Prometheus alert rule therefore changes the ConfigMap's name, which changes the Deployment's pod spec, which rolls the pod automatically. Committed ConfigMap YAML would leave the old copy mounted until someone remembered to restart — a class of bug where the config on disk and the config in the process silently disagree.

The same source files feed Compose and Kubernetes, so an alert rule is written once and runs in both.

Why infra/kustomization.yaml is not inside infra/k8s/base/

kustomize refuses to read a file outside the directory containing kustomization.yaml (LoadRestrictionsRootOnly, the default). The Prometheus rules, Grafana dashboards and Alertmanager template it needs all live under infra/, so the root has to be infra/.

The overlay: deploy/azure/

After ADR 0023 it changes exactly one thing about the base: the registry the eight images come from.

The overlay no longer names Azure at all; it lives under deploy/azure/ because that is where these VMs happen to run, not because anything in it is coupled to Azure.

Why deploy/ and not infra/overlays/

kustomize errors with "cycle detected" if a base directory contains the overlay pointing at it — and the base root must be infra/ (above). So overlays had to move outside. A mechanical constraint, recorded so nobody spends an afternoon rediscovering it.

The overlay on the overlay: deploy/azure-trial/

Points at ../azure and adds one category of change: CPU and memory requests and limits on every workload.

Why requests are absent from the base and present here

A resource request is a claim about how much of a particular cluster a pod should hold. The base cannot know that; an overlay can. Leaving them out of the base is deliberate, not an omission.

On this cluster they are load-bearing. A pod with no request is BestEffort QoS, and BestEffort is the first thing the kubelet evicts when a node runs short of memory. Spread across three nodes totalling ~8 GiB, that is not survivable. The requests are also what let the scheduler spread the stack sensibly instead of piling it onto whichever node it looks at first.

Storage: three different kinds, and the one that was hard

This is the most interesting engineering in the whole deployment.

Plain

A container's filesystem vanishes when it restarts. A PersistentVolumeClaim (PVC) is a pod saying "I need N gigabytes that survive me." A StorageClass says how that gets provisioned. Access modes matter: ReadWriteOnce (RWO) = one node may mount it; ReadWriteMany (RWX) = many nodes may mount it at once. Block storage — a virtual disk — physically cannot do RWX. Only a network filesystem can.

Kind 1 — local-path, the default class (6 volumes)

PVCSizeModeStatusHolds
data-postgres-020GiRWOBoundThe database
data-kafka-010GiRWOBoundTopic logs
prometheus-data20GiRWOBound90 days of metrics
grafana-data2GiRWOBoundgrafana.db — users, prefs
alertmanager-data1GiRWOBoundSilences, notification state
nfs-server-storage10GiRWOBoundThe bytes behind the shared volume
pcdf-backups20GiRWOPendingNightly dumps — see below

local-path is k3s's built-in provisioner (rancher.io/local-path). It hands out a directory on the node's own OS disk. No Azure managed disks are attached for any of these — they all live inside the three StandardSSD_LRS OS disks you are already paying for. That is why the Azure resource list shows three disks, not ten.

What that trades away

Mobility. A local-path volume physically lives on one node, so its pod is pinned to that node forever. Lose a node and you lose that node's volumes. Right now that means: lose pcdf-master and you lose the database, the Kafka log, and all metrics history, along with the control plane.

The alternative — an Azure managed disk per claim — survives node loss but costs a data-disk slot and money per volume, and a B1ms supports only two data disks. On a trial-shaped cluster, local-path is the right call; on anything real it is not.

Why pcdf-backups is Pending, and why that is correct

local-path uses volumeBindingMode: WaitForFirstConsumer: the volume is not provisioned until a pod actually mounts it. Nothing has mounted pcdf-backups yet, because the only thing that does is the postgres-backup CronJob, whose first run is 02:00 UTC.

This is not a fault. It is deferred binding doing its job — the scheduler places the pod first, then the volume is created on whatever node that pod landed on, rather than provisioning a volume somewhere and constraining the scheduler afterwards.

It would be worth checking again after the first scheduled run: kubectl get pvc pcdf-backups -n pcdf should read Bound by 02:05 UTC.

Kind 2 — pcdf-data, the one shared volume (the hard one)

Two pods must write the same tree at the same time: the watcher sweeps /data/inbox/watch, and the console's upload form writes into /data/inbox/uploads — so a file dropped through the browser lands in the same tree as a file dropped on disk. They are currently on the same node, but nothing guarantees that, and nothing should have to.

That requires ReadWriteMany. On AKS this was azurefile-csi — Azure Files, a managed SMB share. Removing AKS removed that class. The replacement runs inside the cluster:

A single NFS server pod (itsthenetwork/nfs-server-alpine:12), backed by an ordinary ReadWriteOnce local-path volume, exporting it over NFS. A statically-bound PersistentVolume of type nfs points at it, and pcdf-data claims that PV by name.

Two non-obvious details, each of which cost real debugging time

1. The PV references the NFS server by IP, not by DNS name

kubelet mounts NFS volumes from the node's own network namespace, which has no cluster DNS resolver. A name like nfs-server.pcdf.svc.cluster.local resolves fine inside a pod and hangs forever when kubelet tries it on the host — the pod sits in ContainerCreating with no useful error.

So 09-nfs-server.yaml pins the Service's clusterIP: 10.43.187.79, and 12-data-pvc.yaml references that literal address. A pinned IP is what makes the reference stable across re-applies instead of drifting to whatever gets auto-assigned next. If one ever changes, both must change together.

2. The export path is /, not /exports

The image writes its export with fsid=0, which makes /exports the NFSv4 pseudo-filesystem root rather than a path beneath it. A client asking for /exports against an fsid=0 export gets ENOENT — No such file or directory. The export is only reachable at /.

Both of these are the kind of thing that is obvious once known and invisible beforehand. Both are commented in the manifests where the next person will hit them.

Honest limitations of this NFS server
  • Single replica, strategy: Recreate. Not highly available — only shared. If it is evicted or its node dies, everything reading or writing /data stalls until it comes back. That is why the trial overlay gives it a resource request: to keep it out of BestEffort.
  • privileged: true. Kernel NFS export requires it. A privileged container is effectively root on its node — the largest single security concession in the cluster, made for one pod, knowingly.
  • Its data sits on a local-path volume. So the shared volume inherits node-pinning after all: lose pcdf-worker-1 and the shared tree is gone with it.

The documented fallback if you would rather not run it at all: co-schedule the watcher and console with podAffinity and drop the claim to ReadWriteOnce. Works, at the price of pinning both to one node.

Kind 3 — backups

14-postgres-backup.yaml: a CronJob at 0 2 * * * (02:00 UTC) running pg_dump in custom format against the postgres Service, then — the important part — pg_restore --list over the result before reporting success. Keeps 14. Runs the same postgres:18.4-alpine image as the database, so pg_dump's version always matches the server's.

Why verify, and why the script is inlined

A backup nobody has read back is not a backup. Counting TABLE DATA entries in the archive's table of contents is a cheap proof that the file is a real, readable dump and not a zero-byte artifact of a failed run.

The policy already existed as tools/ops/backup.sh and could not be reused verbatim: kustomize will not read files outside its root, and the Postgres image has no checkout of this repo. The two steps are inlined into the CronJob instead, and both files say so.

⚠ This is a backup, not disaster recovery

The dumps land on a PVC in the same cluster as the database they came from. Worse, on local-path, they land on a node's OS disk. A lost node takes the database and its backups.

Copy them off before calling it DR:

kubectl get pods -n pcdf -l job-name --field-selector=status.phase=Succeeded
kubectl cp -n pcdf <backup-pod>:/backups/pcdf-<stamp>.dump ./restore-me.dump

Plain

Pod-to-pod traffic across nodes is carried by flannel VXLAN: the packet is wrapped in a UDP datagram on port 8472 and sent between VM private IPs. That is what NSG rule 130 (node-to-node) is allowing. Azure sees ordinary UDP between two VMs on its subnet; Kubernetes sees a flat pod network.

A Service ClusterIP is not a real address on any interface. It is an iptables/IPVS rule on every node that rewrites the destination to one of the backing pod IPs. This is why 10.43.187.79 can be "pinned" — it is a number in a rule, not an allocated interface.

Path 1 — you run kubectl get pods

  1. Your laptop reads ./kubeconfig → https://172.198.58.10:6443.
  2. Packet arrives at pcdf-master-ip; NSG rule 110 (k3s-api, source 0.0.0.0/0) permits it.
  3. Azure NATs it to 10.0.1.6:6443, where the k3s API server listens.
  4. TLS handshake — the server cert covers 172.198.58.10 because of --tls-san; your client cert authenticates you as system:masters.
  5. The API server reads from its embedded datastore and answers.

Path 2 — you open the review console

  1. kubectl port-forward -n pcdf svc/review-console 8000:8000.
  2. That opens a tunnel through the API server — same port 6443, same authentication. No new port is opened on any VM, and nothing new is exposed to the internet.
  3. The API server proxies to the pod's 10.42.1.8:8000.
  4. localhost:8000/admin/page in your browser is the console.

This is why nothing needs an Ingress to be usable. Port-forward gives operator access with zero additional attack surface — it inherits the API server's authentication rather than adding a second front door.

Path 3 — the one that does not exist yet

Public access to the console would be: install ingress-nginx → it takes ports 80/443 on the nodes (already open, NSG rule 120) → apply 31-review-console-ingress.yaml → cert-manager with a letsencrypt ClusterIssuer provides TLS.

⚠ Read before ever applying that Ingress

The console serves personal data with full provenance — names, emails, phone numbers, raw quarantined rows, and which vendor sold them. Applying the Ingress puts that on a public IP.

It does fail closed: with no pcdf_api_keys configured the console answers loopback only, and through an Ingress every request arrives from somewhere else, so every request is refused with 503. But "fails closed" is a property to rely on when something goes wrong, not a reason to make exposure the default.

Never set PCDF_ALLOW_UNAUTHENTICATED there. It exists for a console on a trusted network; on an Ingress it means no keys are checked at all. And never serve it over plain HTTP — the API key travels in a header.

The seam

⚠ The CRLF trap — a real incident, worth reading once

openssl rand on Git Bash emits CRLF. A carriage return ended up inside the Postgres password.

Everything worked. Postgres initialised with the carriage return, the application read the same file and agreed completely. Only the backup CronJob failed — because it receives the value through an environment variable, which trims whitespace. It failed with password authentication failed: from the one component whose failure is silent until the day it matters.

The fix, now in the README's snippet:

rnd() { openssl rand "$@" | tr -d '\r'; }
kubectl create secret generic pcdf-secrets -n pcdf \
  --from-literal=postgres_password="$(rnd -base64 24)" \
  --from-literal=grafana_admin_password="$(rnd -base64 24)" \
  --from-literal=pcdf_api_keys="$(rnd -hex 32),$(rnd -hex 32)"

Rotating after first boot — two components store the value themselves

Postgres

Reads POSTGRES_PASSWORD_FILE only during initdb, on the very first start with an empty volume. Afterwards the password lives in the database. Changing the Secret alone does nothing.

kubectl exec -n pcdf postgres-0 -- psql -U pcdf_dev -d pcdf \
  -c "ALTER USER pcdf_dev PASSWORD 'the-new-value';"
# then update the Secret to match, and restart everything that reads it
kubectl rollout restart deploy -n pcdf

Grafana

Reads GF_SECURITY_ADMIN_PASSWORD only when it first creates grafana.db. Afterwards it lives on the PVC and a changed Secret is silently ignored — the symptom is "Invalid username or password" while holding what is demonstrably the right value.

GP=$(kubectl get pod -n pcdf -l app=grafana -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n pcdf "$GP" -- grafana cli --homepath /usr/share/grafana \
  admin reset-admin-password 'the-new-value'

The consumers, watcher and console have no such problem — they read the mounted file at startup, so a restart is all they need.

The automountServiceAccountToken: false line, on every pod

Two reasons that happen to point the same way. Mechanically: the secret volume mounts at /run/secrets, and /var/run is a symlink to /run — so Kubernetes' automatic token mount at /var/run/secrets/kubernetes.io/serviceaccount must create a directory inside a read-only mount. It cannot, and the container dies with mkdirat ... read-only file system before any application code runs. On its own terms: nothing here calls the Kubernetes API, so a token it never uses is a credential sitting in a container for no reason.

Why deallocate is safe here, specifically

Disks survive. Every Kubernetes volume is a directory on a node's OS disk (local-path), and those disks persist through deallocation. Postgres, Kafka logs, metrics history and the shared /data tree all come back.

IPs survive, because they are Static. On restart the master answers on 172.198.58.10 again, so the kubeconfig and the API server's certificate SAN both still match. This is the payoff for choosing Static in §05.

Order matters on restart: start the master first and let k3s settle before the workers, or the agents spend their first minute retrying a server that is not up. They do recover on their own — it is just noise in the log.

az vm deallocate (not az vm stop) is the one that stops compute billing. stop shuts the OS down but keeps the machine allocated, and you keep paying.

What broke, and why it broke

Six defects found by running it for real. None was findable by rendering YAML; none was Azure-specific. This is the most useful section in the document.

Why this is written down at all

Every one of these would have failed identically on GKE, EKS or a laptop cluster. They are the difference between "the manifests render" and "the system runs" — and each is fixed in the manifests with a comment at the exact place the next person will hit it.

  1. The secret mount blocked Kubernetes' own service-account token

    Symptom: every pod mounting a secret failed to start with mkdirat ... read-only file system — before any application code ran, so there was nothing in the logs to explain it.

    Cause: the secret volume mounts at /run/secrets. /var/run is a symlink to /run. Kubernetes mounts its token at /var/run/secrets/kubernetes.io/serviceaccount — which means creating a directory inside a read-only secret mount. It cannot.

    Fix: automountServiceAccountToken: false — which is also right on its own terms, since nothing here calls the Kubernetes API.

  2. Kafka refused to start on lost+found

    Cause: a PersistentVolume arrives as a freshly formatted ext4 filesystem, and every ext4 filesystem has a lost+found at its root. Kafka requires its log directory to contain nothing but topic data.

    Fix: point KAFKA_LOG_DIRS at a subdirectory of the mount.

    Why Compose never hits it: a Docker volume is a directory on an existing filesystem, not a filesystem of its own — so there is no lost+found.

  3. Kafka could not resolve its own controller — twice

    KAFKA_CONTROLLER_QUORUM_VOTERS names the broker as kafka-0.kafka, a per-pod DNS name that only exists when the governing Service is headless. The Service was ClusterIP.

    Making it headless exposed the second half: a headless Service publishes no DNS for pods that are not Ready — and the broker cannot become Ready until that name resolves. A deadlock.

    Fix: publishNotReadyAddresses: true.

  4. The shared data volume was unwritable

    Images run as uid 10001; a PersistentVolume arrives owned by root. The watcher could not create the directory it exists to watch.

    Fix: fsGroup: 10001 on the two pods that write /data.

    Why Compose never hits it: a bind mount inherits the ownership of a host directory the user already owns.

  5. The migrate Job gave up too early

    backoffLimit: 3 expires about a minute in — which on a cold cluster is while Postgres is still attaching its disk and running initdb. The Job went permanently Failed and had to be deleted and recreated by hand.

    Fix: raised to 10. Costs nothing when the schema is already there (first attempt succeeds) and covers a slow first boot. The live snapshot's migrate pod shows 3 restarts before Completed — this fix earning its keep.

  6. The one that wasted the most time: a carriage return in a password

    Operational rather than structural, and the most instructive. Covered in full in §12. The lesson generalises: a value that is read two different ways can be wrong in only one of them, and the component that notices is the one whose failure you see last.

Two more found on the k3s migration

Both in §10, both about the NFS server: kubelet mounting NFS from a namespace with no cluster DNS (hence the pinned ClusterIP), and fsid=0 making the export reachable only at /. Add the missing nfs-common package (§06) and that is three separate ways the same volume can fail to mount, each with an error message that does not name its cause.

It exchanges an operational guarantee for portability. 0021 → 0022: from a script to a plan

create-cluster.sh was a good script — it checked quota and resource-provider registration before spending money, and it asked for confirmation. It was still imperative: run it twice with different defaults and there is no diff to review, only two clusters that happen to differ. The provisioning record lived in whatever the operator remembered to write down.

Terraform replaced it because terraform plan shows what would change before it changes. The script's confirmation prompt only ever confirmed "create," never "here is the diff."

0022 → 0023: closing the last gap

Asked directly — are we locked into Azure at all? — the honest answer under 0022 was "only for the cluster and the registry, and here is exactly how much." That is a smaller answer than "not at all."

AKS and ACR sat exactly on ADR 0021's line: not above it (neither is a managed database or broker), but not nothing either. Both are Azure services with their own APIs, and a cluster provisioned through them is provisioned through Azure-specific code no matter how generic what runs inside it is.

Removing them left the VM — the one thing every cloud, and a rack in a closet, sells the same way.

Note on ADR 0022's arithmetic

ADR 0022 and 0023 both describe a default shape of Standard_D4as_v5 nodes needing 12 vCPUs. That is no longer true — variables.tf now defaults to B2s + 2×B1ms = 4 vCPU, and the region moved to indiasouthcentral to make it possible (§03). The ADRs record the decision as taken at the time and were not rewritten; variables.tf is the current truth. See §19.

Related reading in this repo: docs/cutting-the-aks-cord.html tells the 0023 migration as a two-person conversation, and docs/pcdf-aks-runbook.html is the AKS-era runbook.

Teardown

⚠ Destructive and irreversible

terraform destroy deletes the three VMs and their OS disks. Every Kubernetes volume lives on those disks — the database, the Kafka log, 90 days of metrics, the shared /data tree. All of it is gone, with no undo. Take and copy out a backup first (§10), and confirm you have it, before running this.

If the intent is only to stop paying, deallocate instead (§15) — it stops compute billing and keeps every byte.

Run — in this order 
# 1. take a backup and copy it OFF the cluster first
kubectl create job -n pcdf --from=cronjob/postgres-backup backup-before-teardown
kubectl wait -n pcdf --for=condition=complete job/backup-before-teardown --timeout=600s
kubectl cp -n pcdf <pod>:/backups/<file>.dump ./restore-me.dump
# verify it locally before continuing
pg_restore --list ./restore-me.dump | head

# 2. review what will be destroyed
terraform -chdir=deploy/azure/terraform plan -destroy \
  -var="ssh_public_key=$(cat ./pcdf-cluster-key.pub)"

# 3. destroy the cluster
terraform -chdir=deploy/azure/terraform destroy \
  -var="ssh_public_key=$(cat ./pcdf-cluster-key.pub)"

# 4. ONLY if the state backend itself is no longer needed
terraform -chdir=deploy/azure/terraform/bootstrap destroy

Step 4 is separate for a reason: destroying the state storage while any environment still uses it as a backend leaves that environment's Terraform unable to find its own state. Do it last, and only when nothing points at it.

NetworkWatcherRG is not managed by Terraform and will remain. Azure recreates it anyway; leave it.
