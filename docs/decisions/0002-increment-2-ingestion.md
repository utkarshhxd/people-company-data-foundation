# ADR 0002: Increment 2 — ingestion

## Status

Accepted.

## Context

Increment 2 implements step 8 of the roadmap: read messy CSV/Excel files and
record every source row as an *observation* with full provenance. It is the
first increment that writes data, so it also forces the two decisions
increment 1 deferred: migration tooling and the first DDL.

Ingestion does no mapping, normalization, validation, or entity resolution.
It answers exactly one question: what did this source literally say, when, and
where did it come from?

## Decisions

- **Migrations: plain numbered `.sql` files + a ~120-line forward-only runner**
  (`libs/common/migrations.py`), tracking applied versions in
  `schema_migrations`. No Alembic/SQLAlchemy (the stack has no ORM — pulling
  SQLAlchemy in to serve migrations alone is a large dependency for one job)
  and no yoyo. The schema here is hand-crafted (JSONB, CHECK constraints,
  targeted indexes), so raw SQL reads better than generated DDL. A sha256
  checksum per migration makes applied migrations immutable: editing one is an
  error, not a silent divergence. A `-- pcdf:no-transaction` marker is
  supported from day one because retrofitting it later would require editing
  an already-applied file, which the checksum check forbids.

- **UUIDs generated by Postgres via `uuidv7()`** (native in PG 18), not in
  Python. `raw_record` is append-heavy and v7's time-ordering gives far better
  B-tree insert locality than v4's randomness. It also enables the ordering
  guarantee below.

- **Commit, then publish.** Records are inserted and committed, the batch is
  marked `completed`, and only then are events published — sourced from a
  *read-back of committed rows* (`iter_committed_records`). This makes it
  structurally impossible to emit an event referencing a row that doesn't
  exist. This is the load-bearing correctness property of the increment.

- **The dual-write problem is surfaced, not hidden.** If Kafka is unreachable
  after commit, rows exist with no events. Rather than pretend otherwise,
  `batch.events_published_at` stays NULL, the CLI exits 4, and the gap is
  queryable and replayable. **Postgres is the source of truth; Kafka is a
  derived notification.** Downstream stages must only read batches with
  `status = 'completed'`.

- **Atomic per batch.** All of a file's records commit in one transaction — a
  file is either fully ingested or not at all, so there is no partial state to
  reason about. Chunked commits would be faster on very large files; per the
  project's "correctness and explainability over premature optimization" rule,
  atomicity wins until a real file makes it hurt.

- **`executemany` in chunks of 1000, not `COPY`.** psycopg3 pipelines
  `executemany` efficiently and adapts `jsonb` cleanly, whereas COPY's text
  format needs manual escaping care for JSON. COPY is the documented
  optimization path if profiling later demands it.

- **Re-ingestion is detected, not blocked.** `batch.file_hash` (sha256 of file
  bytes) makes a repeat ingestion visible; the CLI refuses with exit 3 unless
  `--allow-reingest` is passed. Hard-blocking would make legitimate re-runs
  painful; silently duplicating would corrupt counts.

- **`source_record_id` defaults to the row number**, overridable with
  `--record-id-column`. Most vendor CSVs have no stable natural key; the row
  number is at least deterministic per file. It is only unique within a batch
  unless a natural key is supplied.

- **Source reliability is its own column** on `source`, deliberately separate
  from the mapping confidence, validation result, and match confidence that
  later increments introduce. The spec is explicit that these four must never
  be conflated.

- **Topics created explicitly via AdminClient** (3 partitions, RF 1), not left
  to Kafka's `auto.create.topics.enable`, which silently yields 1 partition
  and default config. Events carry references only — never payloads — per the
  "don't put files in Kafka" rule. `event_version` is present from day one so
  the shape can evolve without guessing what consumers hold.

- **New dependency `fastexcel`**: Polars' `read_excel` needs an engine, and
  calamine (via fastexcel) is its Rust-based default — no openpyxl, consistent
  with the Polars-centric stack. Only needed because the spec names Excel as
  an input format.

- **Metrics: the `batch` table, not Prometheus.** The ingestion CLI is
  short-lived and Prometheus is pull-based, so a scrape target never exists. A
  Pushgateway would be new infrastructure serving one job — not yet justified.
  Row counts live in `batch` because provenance needs them anyway. Natural
  next step when more pipeline stages exist: provision a Grafana **Postgres**
  datasource and read `batch` directly, which needs no new containers.

- **`Settings` moved to `libs/common/config.py`** and
  `services/api/src/api_service/config.py` was **deleted** rather than left as
  a re-export shim. Both services need identical Postgres/Kafka config.

## Never destroy raw source information

The central guarantee. `readers.py` disables type inference everywhere
(`infer_schema=False` for CSV, `infer_schema_length=0` for Excel) because
inference is exactly what turns `00501` into `501`, long IDs into scientific
notation, and phone numbers into floats. `tests/test_readers.py` asserts this
against a deliberately hostile fixture and verified end-to-end in Postgres:

| Source value | Stored as | Would have become |
|---|---|---|
| `00501` | `00501` | `501` |
| `12345678901234567890` | unchanged | `1.2345678901234567e19` |
| `9.99E10` | `9.99E10` | `99900000000.0` |
| `  JOHN  SMITH  ` | padding preserved | trimmed |
| `José Ünicode` | unchanged | mojibake |
| `01/02/2026` | unchanged | reformatted/ambiguous |

Whitespace, casing, and formatting are deliberately **not** cleaned here —
that is the normalizer's job in a later increment, and it needs the original
to work from.

### Accepted fidelity limit

Polars collapses `a,,b` and `a,"",b` to the same value; the
missing-vs-empty-string distinction is lost either way
(`missing_utf8_is_empty_string` only flips which way it collapses). Accepted
and documented. The property that matters — no type coercion of any value — is
fully preserved. If the distinction ever matters, the CSV branch can move to
stdlib `csv` in ~20 lines without touching anything else.

## Operational fixes found during end-to-end verification

- **The `migrate` image baked migrations in at build time** (`COPY db/ db/`),
  so `docker compose run --rm migrate` read a stale copy — a newly added
  migration would silently report "0 applied" until someone rebuilt. Found by
  deliberately tampering with an applied migration and watching the checksum
  guard *fail to fire*. Fixed by bind-mounting `./db:/app/db:ro` so the runner
  always sees current files. This is a good argument for testing that safety
  guards actually trip, rather than assuming they do.

- **Git Bash mangles container paths.** `/data/inbox/x.csv` gets rewritten to
  `C:/Program Files/Git/data/inbox/x.csv` by MSYS path conversion. Run
  `docker compose run` from PowerShell (or set `MSYS_NO_PATHCONV=1`).

- **Native extensions cannot run on this Windows host.** Polars, `psycopg
  [binary]`, and `confluent-kafka` are all compiled extensions, and the host's
  Application Control policy blocks their DLLs (and `.exe` console-script
  shims) outside Docker. All tests therefore run in containers:
  `docker compose run --rm ingestion python -m pytest tests`.
